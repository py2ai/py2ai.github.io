BasicSR: Reading the Config-Driven Restoration Framework End to End

28 Oct 2026  ·  12 mins read

Contents

If you have ever downloaded a Real-ESRGAN checkpoint and wondered what actually produced it, the answer is BasicSR. The repository, maintained by the XPixelGroup, is an open source PyTorch toolkit for image and video restoration — super resolution, denoising, deblurring, deraining, face restoration — and version 1.4.2 is the version Real-ESRGAN, SwinIR fine-tunes, and a long tail of papers were actually trained with. Unlike a research one-off, BasicSR is deliberately shaped like a framework: a YAML file in, trained checkpoints out, with every moving part selected by string lookup rather than code edits.

What makes it worth a source tour is how much work gets done by how little code. The whole training engine is one file of roughly two hundred lines. Around it, four registries — datasets, models, architectures, losses — let a config key like PairedImageDataset or SwinIR summon a class that was auto-imported from a directory scan at startup. Nothing is hidden behind magic metaprogramming you cannot trace: every lookup lands in a hundred-line registry class you can read in one sitting.

This post walks the framework from the entry point down: the driver that owns the loop, the data assembly layer that feeds it, the model core where gradients happen, and the architecture, loss, and metric registries that plug in around it. Two diagrams accompany the text — an overview map first, then a deeper graph once we reach the model core. Everything cited below links to real lines in the repository at the commit we read.

The overview map: the training driver on the left pulls config, datasets, and models together; every builder on the right of the registries is a config-key lookup.

Reading the overview from left to right:

  • parse_options, L99 — merges the YAML config with CLI arguments, resolves distributed settings, and plants a deterministic random seed before anything else runs.
  • create_train_val_dataloader, L29 — splits opt['datasets'] into one train phase and any number of val_ phases, computing total epochs from total_iter and the enlarged sampler ratio.
  • build_dataset, L25 — a one-line registry lookup: the type key in the dataset config selects the class, so switching from LMDB to folders is a YAML edit, not a code edit.
  • build_model, L18 — the same trick for models: model_type: SRModel instantiates the reference trainer that most other models inherit from.
  • SRModel, L15 — builds the generator network, both losses, optimizers, and EMA, then owns the per-iteration logic every experiment actually executes.
  • optimize_parameters, L92 — the heart of the framework in a dozen lines: forward pass, pixel and perceptual losses, backward, optimizer step, EMA update.
  • Registry, L4 — the generic name-to-class map that all four registries are instantiated from; it also implements the _basicsr suffix fallback that keeps third-party forks compatible.

From Install to Your First Model

BasicSR installs like a plain library: pip install basicsr pulls the package, and the optional basicsr extra gates compiled ops such as the deformable convolution used by some video models. Running an experiment is the classic two-argument invocation: python basicsr/train.py -opt options/train/SRResNet_SRVGG/netD_....yml in the repo layout, or any YAML you author yourself. The file basicsr/train.py ends with a __main__ guard that passes the repo root into the training driver, and from that moment the YAML is the single source of truth.

A minimal config has four stanzas. network_g names the generator and its constructor arguments; model_type selects the trainer class; datasets holds a train block and one or more val blocks; and train carries iteration counts, pixel_opt (the pixel loss), optionally perceptual_opt, and the optimizer schedule. The driver copies the YAML verbatim into the experiment directory via copy_opt_file, so every checkpoint folder is self-describing — a small habit that saves enormous amounts of forensic work later.

One design decision deserves attention before we go deeper: BasicSR counts iterations, not epochs. The config sets total_iter, and create_train_val_dataloader divides it by iterations-per-epoch only to report a nominal epoch count in the log. This is because the EnlargedSampler, L6 can repeat a small dataset many times per pass through the loader via dataset_enlarge_ratio, a trick that keeps the learning-rate schedule and logging frequency independent of dataset size. If you arrive from classification frameworks where epochs are the currency, this inversion is the first mental shift to make.

The Driver: Options In, Iterations Out

The training driver in basicsr/train.py reads top to bottom like a checklist. After parse_options, load_resume_state implements auto-resume: it scans experiments/<name>/training_states for .state files, parses the iteration number out of the filename, and resumes from the largest one. When nothing is resumable, make_exp_dirs creates the experiment skeleton — models, training states, logs, and visualization folders — while a guard refuses to overwrite an existing directory unless overwrite is set, protecting you from silently clobbering a long run.

Logging is wired twice: the file logger comes from get_root_logger, L146, writing train_<name>_<timestamp>.log under the experiment path, and the metric logger is MessageLogger, L45, which formats iteration, learning rates, elapsed and remaining time, and the model’s log_dict every print_freq iterations. TensorBoard and wandb are initialized only when the config asks for them and the run name is not a debug one — a thoughtful detail that keeps smoke tests off your dashboards.

The loop itself is a prefetch-then-consume pattern. A CPUPrefetcher, L61 wraps the DataLoader so the driver calls prefetcher.next() instead of iterating; on CUDA, CUDAPrefetcher, L82 moves each batch to the GPU from a side stream, and the driver enforces pin_memory=True for that mode with an explicit error. Each iteration then runs exactly four model calls: update_learning_rate (warmup-aware), feed_data, optimize_parameters, and periodic save plus validation based on save_checkpoint_freq and val_freq. That symmetry is the framework’s real contract: a new model type only has to implement those methods and the driver will train it unchanged.

Data Assembly: Pairs, Patches, and Prefetch

The data layer is anchored by dataset classes rather than a monolithic processing chain, and each one is small enough to fully internalize. PairedImageDataset, L11 handles the canonical restoration case of LQ/GT image pairs and supports three path modes: LMDB pairs, a meta-info text file, or plain folder scanning. All I/O flows through FileClient, L132, a dispatcher keyed by the io_backend config that hides whether bytes come from disk, memory, or an LMDB hash — the reason the same dataset works for quick experiments and production-scale LMDB corpora without code changes.

The per-item processing chain in __getitem__ is worth reading line by line. Bytes are decoded by imfrombytes into HWC BGR float arrays in [0, 1]; then, only in the train phase, paired_random_crop, L26 cuts spatially aligned patches — it picks the LQ window first and multiplies its coordinates by the scale factor for the GT crop, raising a loud error if the pair geometry or patch size is inconsistent. augment, L94 then applies the same random horizontal flip and 90-degree rotation family to both images of the pair so alignment survives. Finally img2tensor converts to CHW RGB tensors, and optional mean/std normalization closes the item.

The sibling classes cover the other regimes: SingleImageDataset, L11 serves LQ-only images for blind testing without ground truth, and the Real-ESRGAN-specific datasets synthesize degradations on the fly. Downstream, build_dataloader in the data package assembles the loader — it multiplies per-GPU batch size and worker count by the GPU count in non-distributed mode, seeds workers deterministically with a rank-aware worker_init_fn, and switches to a queue-backed PrefetchDataLoader when CPU prefetching is configured. For benchmark validation, mod_crop in the transforms module trims image borders so dimensions divide by the scale factor, the small detail that keeps PSNR comparisons against other papers honest.

The detail graph zooms in: dataset classes on the left, the model core in the center, and the three plugin registries — architectures, losses, metrics — hanging off the config keys.

The Model Core: One Trainer to Extend

Everything in BasicSR ultimately lands in two model files. BaseModel, L13 is the infrastructure half: scheduler setup, warmup-aware update_learning_rate, device and DDP wrapping via model_to_device, and the checkpoint machinery — save_network, load_network, save_training_state, and resume_training, which restores both optimizer and scheduler state so a resumed run is bit-identical in schedule terms. Its validation method dispatches to a distributed or non-distributed path, which is the only place multiprocessing awareness leaks into model code.

SRModel, L15 is the reference implementation, and reading it is the fastest way to learn the framework’s extension idiom. init_training_settings shows the assembly order: optional EMA network built from the same network_g spec, then build_loss, L19 called twice — once for pixel_opt, once for perceptual_opt — then setup_optimizers, which collects only parameters with requires_grad and warns about the rest. The pixel loss is usually L1Loss, L28, optionally swapped for Charbonnier or MSELoss, L56; the perceptual path wraps VGG features in PerceptualLoss, L147 with an optional style term. GAN-based variants add a discriminator and GANLoss, L11, and the weighted_loss decorator in the loss utilities handles per-element weighting for the WGAN-family penalties.

The per-iteration method is refreshingly plain. optimize_parameters zeroes gradients, runs self.net_g(self.lq), sums the configured losses into a single l_total, backpropagates, steps the optimizer, reduces the loss dict for logging, and applies the EMA decay. There is no gradient accumulation, no AMP, no hook framework — just the PyTorch basics, which is exactly why it is such a good template: when you subclass to add, say, frequency-domain losses, there is nothing to fight. Validation is equally explicit: nondist_validation loops the val loader, converts outputs with tensor2img, L38, accumulates each configured metric through calculate_metric, L10 — typically calculate_psnr, L12 or calculate_ssim, L85, both MATLAB-faithful with crop-border and Y-channel options — and tracks the best value per dataset for model selection.

The architecture registry works exactly like the others: every *_arch.py file under basicsr/archs is auto-imported, and network_g.type selects the class. The shelf is deep — RRDBNet, L67 for the ESRGAN lineage, EDSR, L9 for the BN-free residual classic, and SwinIR, L694, whose window-attention RSTB blocks follow the same design we covered in our Swin Transformer tour. Shared initialization helpers like default_init_weights live in arch_util.py, so a custom backbone only needs the class plus a decorator to become a one-line config option.

Honest Limits

The framework’s simplicity has edges you should know before betting a deadline on it. Validation is rigid: build_dataloader hard-codes batch size 1 for val phases, and the driver warns that multiple validation datasets are only supported by SRModel — video and GAN model classes do not all honor that path. EMA weights live in an unwrapped net_g_ema, so distributed testing with EMA is a single-GPU convenience rather than a scaled-out feature, and the checkpoint for EMA is stored under a separate params_ema key that your inference script must request explicitly.

Training features are equally minimal by choice. There is no mixed precision in optimize_parameters, no gradient clipping, no gradient accumulation, and no native scheduling of the validation cadence beyond a fixed val_freq — the Framework expects you to subclass for all of that. The iteration-centric design also means small datasets with a large dataset_enlarge_ratio can produce misleading per-epoch logs, and auto-resume picks the lexicographically newest .state file, so renaming checkpoints carelessly can confuse recovery. Finally, degraded training for Real-ESRGAN-style blind restoration lives in the dedicated degradation datasets and the degradations module, not in SRModel itself — if you want blind SR you must switch model_type and dataset type together, or your model will train on clean pairs while believing otherwise. Where you need differentiable geometry or color ops beyond the provided transforms, Kornia composes cleanly with these dataset classes, and if your destination is diffusion-based img2img restoration, our Stable Diffusion tour is the natural next read — Real-ESRGAN’s own docs use it as the reference integration target.
