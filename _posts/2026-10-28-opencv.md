OpenCV is the library that every other computer vision tool gets compared to. Twenty-plus years in, it is the default import in tutorials, the runtime under countless factory robots and security cameras, and the compatibility target that newer frameworks measure themselves against — [Kornia](/kornia/), for instance, exists precisely because OpenCV's kernels are not differentiable, and [MediaPipe](/mediapipe/) leans on the same C++ sensibility for its own graph machinery. Yet despite the ubiquity, surprisingly few people have read the source. The repository looks monolithic, the C++ is dense, and the Python experience is so smooth that the machinery underneath becomes invisible. This post is a tour of that machinery on the `5.x` branch, which is now the default branch of `opencv/opencv`.

The repository is organized as a set of self-contained modules under `modules/`, and each module is effectively a layered library: a public header API on top, dispatch code that selects CPU SIMD paths or GPU paths in the middle, and algorithmic kernels at the bottom. We narrowed the tour to the four modules that matter most for the `cv2` experience: `core` (the `Mat` container, the allocator, the thread pool, the OpenCL runtime, and the `FileStorage` serializer), `imgproc` (the classic kernels: resize, blur, edges, color conversions), `dnn` (the inference engine that reads ONNX and other formats), and `python` (the binding generator and runtime bridge that turns all of the above into a single importable module).

The method is the same as in our other source tours: we mapped the subsystems into two architecture diagrams — an overview and a detail view — and then walked each one with line-linked references, so every claim below links to a real function at a real line that you can open in your browser. A note on scope: this is a genuinely large codebase (the four modules we checked out contain over seven thousand files), so the tour favors the load-bearing files over exhaustive coverage.

## Reading the overview from left to right:

- **The bridge.** [PyInit_cv2, L621](https://github.com/opencv/opencv/blob/5.x/modules/python/src2/cv2.cpp#L621) is the CPython module entry point; it delegates to [init_body, L482](https://github.com/opencv/opencv/blob/5.x/modules/python/src2/cv2.cpp#L482), which registers every generated submodule, type, and constant you see under `import cv2`. The special method [pycvRegisterMatType, L105](https://github.com/opencv/opencv/blob/5.x/modules/python/src2/cv2.cpp#L105) lets the NumPy-facing wrapper register its own `Mat` type back into the module.
- **Conversion.** [pyopencv_to, L75](https://github.com/opencv/opencv/blob/5.x/modules/python/src2/cv2_convert.cpp#L75) is the workhorse that turns a Python object into a `cv::Mat`, typically by borrowing a NumPy buffer rather than copying it. Around it live two RAII helpers in [cv2_util.hpp, L22](https://github.com/opencv/opencv/blob/5.x/modules/python/src2/cv2_util.hpp#L22) and [L34](https://github.com/opencv/opencv/blob/5.x/modules/python/src2/cv2_util.hpp#L34): `PyAllowThreads` drops the GIL so C++ workers can run concurrently, and `PyEnsureGIL` reacquires it when callbacks need Python again.
- **The container.** Everything pixel-shaped is a `Mat`. [Mat::create, L1072](https://github.com/opencv/opencv/blob/5.x/modules/core/src/matrix.cpp#L1072) allocates or reshapes it, backed by the cache-line-aligned allocator [fastMalloc, L130](https://github.com/opencv/opencv/blob/5.x/modules/core/src/alloc.cpp#L130). The GPU shadow twin is [UMat::create, L360](https://github.com/opencv/opencv/blob/5.x/modules/core/src/umatrix.cpp#L360), whose buffers live in an OpenCL context built by [initializeContextFromHandle, L3220](https://github.com/opencv/opencv/blob/5.x/modules/core/src/ocl.cpp#L3220).
- **Persistence.** [FileStorage::open, L2028](https://github.com/opencv/opencv/blob/5.x/modules/core/src/persistence.cpp#L2028) parses and writes YAML, XML, and JSON documents, and [FileStorage::operator[], L2111](https://github.com/opencv/opencv/blob/5.x/modules/core/src/persistence.cpp#L2111) returns a `FileNode` cursor for key lookups. This is the machinery under `cv::imwrite`, camera calibration files, and model configuration files.
- **Kernels.** [cv::resize, L3580](https://github.com/opencv/opencv/blob/5.x/modules/imgproc/src/resize.cpp#L3580) dispatches to interpolation-specific implementations; the generic path builds a per-row [resizeGeneric_Invoker, L1785](https://github.com/opencv/opencv/blob/5.x/modules/imgproc/src/resize.cpp#L1785) and hands it to the thread pool. [GaussianBlur, L526](https://github.com/opencv/opencv/blob/5.x/modules/imgproc/src/smooth.dispatch.cpp#L526) runs separable row and column filters in parallel, and [Canny, L683](https://github.com/opencv/opencv/blob/5.x/modules/imgproc/src/canny.cpp#L683) computes gradients and then tracks edges with its own [parallelCanny, L220](https://github.com/opencv/opencv/blob/5.x/modules/imgproc/src/canny.cpp#L220) loop body.
- **Color.** [cvtColor, L192](https://github.com/opencv/opencv/blob/5.x/modules/imgproc/src/color.cpp#L192) is one giant conversion switch covering dozens of color space pairs, each with an OpenCL fast path attempted first.
- **Inference.** [readNet, L13](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/dnn_read.cpp#L13) auto-detects the model format and lands ONNX files at [readNetFromONNX, L72](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/onnx/onnx_importer.cpp#L72). At run time, [Net::forward, L76](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/net.cpp#L76) delegates into the implementation, which validates the backend, fuses layers, and executes them one by one.

## The Detail View: Following One Call Through the Stack

<div style="overflow-x:auto;"><img src="/assets/img/diagrams/opencv/opencv-opencv-architecture.svg" alt="OpenCV detail diagram: binding internals, core runtime, kernels, DNN frontend, layers and backends" style="min-width:900px;"></div>

<p><em>The detail graph expands each group: the binding internals on the left, the core runtime that everything shares, the imgproc kernels, and the DNN frontend feeding the layer zoo and backend dispatch.</em></p>

Follow `net.forward()` from Python and the detail graph comes alive. The public [Net::forward, L76](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/net.cpp#L76) is three lines of assertion plus a delegate. The implementation first runs [Net::Impl::setUpNet, L190](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/net_impl.cpp#L190), which validates the backend and target pair and allocates every layer's blobs. If this is the first forward pass, graph optimization kicks in: [Net::Impl::fuseLayers, L35](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/net_impl_fuse.cpp#L35) merges convolution + batch norm + scale + activation chains into single nodes, which is where most of the real-world speedup of OpenCV's inference lives. Then execution proceeds layer by layer through [Net::Impl::forwardLayer, L698](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/net_impl.cpp#L698), which looks up the layer's backend node via the [preferableBackend, L143](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/net_impl_backend.cpp#L143) dispatch, falls back to the CPU implementation when no specialized backend claims the layer, and optionally runs the whole thing on OpenCL `UMat` blobs.

The layer zoo is where the 5.x branch gets interesting. The classic float path still lives in [ConvolutionLayerImpl, L200](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/layers/convolution_layer.cpp#L200), but a new engine has appeared alongside it: [Conv2LayerImpl, L34](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/layers/conv2_layer.cpp#L34) with explicit parallel tile loops, [GemmLayerImpl, L55](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/layers/gemm_layer.cpp#L55) with threaded GEMM blocks, and — the headline — [SDPALayerImpl, L15](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/layers/sdpa_layer.cpp#L15), scaled dot-product attention. Combined with [KVCacheManager::reserve, L143](https://github.com/opencv/opencv/blob/5.x/modules/dnn/src/kv_cache_manager.cpp#L143), which wires per-layer key-value caches into the net, OpenCV's DNN module is quietly becoming capable of running autoregressive transformer models, not just convolutional classifiers.

## From Install to Your First Model

Installation is one pip command, and the first useful program exercises both halves of the graph — classic kernels and the inference engine:

```python
import cv2
import numpy as np

# classic imgproc path: color, blur, edges
img = cv2.imread("scene.jpg")
gray = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)   # color.cpp dispatch
gray = cv2.GaussianBlur(gray, (5, 5), 0)       # smooth.dispatch.cpp
edges = cv2.Canny(gray, 50, 150)               # canny.cpp

# dnn path: ONNX model inference
net = cv2.dnn.readNetFromONNX("mobilenetv2.onnx")
blob = cv2.dnn.blobFromImage(img, scalefactor=1.0/255.0,
                             size=(224, 224), swapRB=True)
net.setInput(blob)
out = net.forward()                            # net.cpp -> net_impl.cpp
print(out.shape)                               # (1, 1000, ...)
```

A few practical notes that the source makes obvious. First, `cv2.GaussianBlur` and `cv2.Canny` release the GIL while they run (every generated binding wraps its call in `PyAllowThreads`), which means you can run multiple OpenCV calls from multiple Python threads and actually get parallelism — a rare property among Python libraries. Second, the blob preprocessing in `cv2.dnn.blobFromImage` exists because the DNN module expects normalized, channel-swapped, batched float tensors; the conversion from your BGR `uint8` Mat to that layout is explicit rather than magical. Third, if the model output looks wrong, check the channel order first: the library's BGR convention leaks everywhere, which is exactly the friction [Kornia](/kornia/) was built to eliminate for PyTorch users. For detection and segmentation models that consume these edge and blob outputs, our [Ultralytics](/ultralytics/) and [ONNX](/onnx/) tours cover the consumer side.

## Under the Hood: Threads, Memory, and the GIL

Three systems make every kernel above fast, and they are worth reading in their own right. The thread pool entry point [parallel_for_, L513](https://github.com/opencv/opencv/blob/5.x/modules/core/src/parallel.cpp#L513) takes a `Range` and a loop body, and its implementation [parallel_for_impl, L558](https://github.com/opencv/opencv/blob/5.x/modules/core/src/parallel.cpp#L558) decides whether to use the internal pool, TBB, or OpenMP, splitting the range into stripes sized by the caller's hint. [setNumThreads, L722](https://github.com/opencv/opencv/blob/5.x/modules/core/src/parallel.cpp#L722) caps the worker count globally, and it is the first knob to reach for when OpenCV oversubscribes a container that already runs its own pool. Memory management is deliberately boring: [fastMalloc, L130](https://github.com/opencv/opencv/blob/5.x/modules/core/src/alloc.cpp#L130) allocates aligned blocks, and `Mat` reference counting means the Python side can pass buffers around without deep copies as long as nobody writes in place — the reason Canny refuses in-place input for RGB sources (see the assertion at [Canny, L683](https://github.com/opencv/opencv/blob/5.x/modules/imgproc/src/canny.cpp#L683)). And when a kernel claims GPU capability, it is usually the `UMat` path through the OpenCL runtime in `ocl.cpp`, whose contexts and command queues are constructed independently of any particular framework — a design that keeps OpenCV usable on machines where CUDA is not an option.

## What the 5.x Branch Changes

The default branch is no longer the 4.x you may have pinned. Three shifts stand out from the source. The DNN module is growing transformer-native layers — attention, GEMM, rotary embeddings, RMSNorm, and the KV cache manager — moving it from "runs MobileNet" toward "runs small language models," which changes what `cv2.dnn` is for. The binding generator under `modules/python/src2` now also produces typing stubs (`typing_stubs_generator.py`), so IDE autocompletion for `cv2` comes from the same headers that generate the C++ wrappers, keeping signatures honest. And the codebase continues its long migration toward pluggable engine selection inside DNN: the ONNX reader resolves between the built-in engine and ONNX Runtime when built with `WITH_ONNXRUNTIME`, an early example of what is effectively a modular inference strategy inside the library.

## Honest Limits

The C++ weight is real. The Python layer is generated glue; when something misbehaves you end up reading C++ stacks, and the binding generator's conventions (in-place output arrays, `None` handling, NumPy striding) are a language of their own. The DNN module is inference-only — there is no training story here, so it complements rather than replaces the training frameworks we have covered. Performance is uneven across the matrix of backends and targets: the CPU SIMD paths are excellent and battle-tested, but the CUDA, Vulkan, and WebNN backends each cover different op subsets, and a model that runs on one target may silently fall back to CPU per-layer on another, which is why `net_impl.cpp` carries explicit backend-unsupported errors. The `UMat`/OpenCL path is portable but its speed depends heavily on your vendor's OpenCL runtime. Finally, `5.x` is a moving default branch: the line numbers linked here are accurate today, and the transformer-era DNN layers in particular are still visibly under construction.

If you want the differentiable counterpart to everything in `imgproc`, read [Kornia](/kornia/) next; if you want to see where these pixels go in production systems, [MediaPipe](/mediapipe/) shows the graph-execution descendant of the same design school.
