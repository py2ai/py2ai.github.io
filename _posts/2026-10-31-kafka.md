Every AI system eventually hits the same wall: your models are only as good, and only as fresh, as the events that reach them. Feature vectors generated a few seconds after a user click, GPU utilization samples scraped off a training node, inference requests and their latencies, token-by-token usage records from an LLM gateway — all of these arrive as continuous streams of facts, and batching them through cron jobs or message queues that silently drop data stops scaling fast. This is the gap Apache Kafka was built to fill, and it is why Kafka sits upstream of so many ML feature stores, real-time dashboards, and telemetry backends (often right next to a columnar sink like [ClickHouse](/clickhouse/)).

Kafka's core idea is deceptively simple: a distributed, append-only commit log. Producers append records to the end of partitioned logs; consumers read them at their own pace by keeping an offset — a pointer into the log — rather than by deleting messages. Because the log is durable and replayable, the same stream can feed a live dashboard, a training-data dump into object storage, and an online feature extractor simultaneously, each with its own position. Fault tolerance comes from replicating each partition across brokers, with a high-watermark defining what has been safely copied and therefore what consumers are allowed to see.

In this post we read the actual implementation on the `trunk` branch of apache/kafka — the Scala/Java broker core plus its Java clients. Two architecture diagrams follow: a high-level overview, and a detailed map of the classes that carry every message from a producer's `send()` call to a consumer's `poll()`. All class and line references link into the real sources on GitHub, so you can follow along in your editor.

Reading the overview from left to right:

- [KafkaProducer.send, L1027](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/producer/KafkaProducer.java#L1027) serializes the record, runs it through interceptors, and picks a destination partition — either one you set, or computed in `partition()` at [L1681](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/producer/KafkaProducer.java#L1681).
- [RecordAccumulator.drain, L1083](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/producer/internals/RecordAccumulator.java#L1083) collects the batches that are ready to go, capped by the max request size per node.
- [Sender.run, L241](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/producer/internals/Sender.java#L241) is the producer's I/O loop; it turns drained batches into `ProduceRequest` RPCs via [sendProduceRequest, L896](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/producer/internals/Sender.java#L896).
- [SocketServer, L71](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/network/SocketServer.scala#L71) accepts connections with an Acceptor (L458) and reads and decodes requests in Processor threads (L779), enqueueing them into a bounded queue.
- [KafkaRequestHandler.run, L108](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/KafkaRequestHandler.scala#L108) pulls requests off that queue and dispatches them at [L167](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/KafkaRequestHandler.scala#L167) to the API layer.
- [KafkaApis.handleProduceRequest, L401](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/KafkaApis.scala#L401) is the protocol facade every client request crosses; fetches enter at [handleFetchRequest, L568](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/KafkaApis.scala#L568).
- [ReplicaManager.appendRecordsToLeader, L586](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/ReplicaManager.scala#L586) checks the ISR and required acks, then routes the write through a Partition to the log.
- [UnifiedLog.appendAsLeader, L1033](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/UnifiedLog.java#L1033) appends to the active segment and rolls it when it grows too large ([maybeRoll, L2166](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/UnifiedLog.java#L2166)).
- [GroupCoordinatorService.joinGroup, L1009](https://github.com/apache/kafka/blob/trunk/group-coordinator/src/main/java/org/apache/kafka/coordinator/group/GroupCoordinatorService.java#L1009) runs consumer-group rebalancing and offset commits on the new KRaft-era coordinator runtime.

## The Broker: From Socket to Commit Log

The request path is deliberately boring, which is why it is fast. `SocketServer` (class at [L71](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/network/SocketServer.scala#L71)) multiplexes NIO sockets: one `Acceptor` per listener ([L458](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/network/SocketServer.scala#L458)) hands new connections to `Processor` threads ([L779](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/network/SocketServer.scala#L779)) that decrypt, parse frame headers, and enqueue complete requests. A fixed pool of `KafkaRequestHandler` worker threads — sized by `num.io.threads` and resizable at runtime through [KafkaRequestHandlerPool, L227](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/KafkaRequestHandler.scala#L227) — drains the queue held by [RequestChannel, L40](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/network/RequestChannel.scala#L40), and replies travel back through [sendResponse, L91](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/network/RequestChannel.scala#L91).

`KafkaApis` ([class, L95](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/KafkaApis.scala#L95)) is the switchboard: produce requests go to `handleProduceRequest` ([L401](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/KafkaApis.scala#L401)), fetches to `handleFetchRequest` ([L568](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/KafkaApis.scala#L568)), offset reads to `handleOffsetFetchRequest` ([L1029](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/KafkaApis.scala#L1029)), and group membership to `handleJoinGroupRequest` ([L1390](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/KafkaApis.scala#L1390)). Each handler validates the request, calls into the right subsystem, and registers a callback that completes the response asynchronously — the handler thread is never blocked waiting for a disk write or a quorum ack.

The replication brain lives in `ReplicaManager` ([class, L154](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/ReplicaManager.scala#L154)). `appendRecordsToLeader` ([L586](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/ReplicaManager.scala#L586)) refuses writes if the partition has no elected leader or the ISR has shrunk below `min.insync.replicas`; the actual append funnels through `appendToLocalLog` ([L1376](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/ReplicaManager.scala#L1376)) into per-partition state held by `Partition` ([class, L163](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/cluster/Partition.scala#L163)). Leadership transitions are explicit — `makeLeader` ([L590](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/cluster/Partition.scala#L590)) and `makeFollower` ([L696](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/cluster/Partition.scala#L696)) — triggered by metadata records from the KRaft controller. Reads flow through `fetchMessages` ([L1665](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/server/ReplicaManager.scala#L1665)), which can park a fetch and defer the response until enough new data arrives, a trick that keeps consumer latency low without busy polling.

## The Storage Engine: Segments, Indexes, Watermarks

One of the bigger architectural shifts of recent Kafka versions is that the log implementation moved from Scala into a plain-Java storage module. The Scala `kafka.log.LogManager` you find in core is now just a factory ([object, L34](https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/log/LogManager.scala#L34)) that instantiates the Java `org.apache.kafka.storage.internals.log.LogManager` ([class, L81](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/LogManager.java#L81)). That Java class owns the log-directory map — `getOrCreateLog` at [L1239](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/LogManager.java#L1239) maps a TopicPartition to its `UnifiedLog` — and background jobs for retention, flushing, and recovery that kick off in `startup()` at [L771](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/LogManager.java#L771).

`UnifiedLog` ([class, L105](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/UnifiedLog.java#L105)) is the per-partition commit log. Leader-side appends go through `appendAsLeader` ([L1033](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/UnifiedLog.java#L1033)), which validates record offsets, updates the leader epoch, and assigns contiguous offsets; follower-side replication enters via `appendAsFollower` ([L1093](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/UnifiedLog.java#L1093)). The write itself is delegated to `LocalLog` ([class, L71](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/LocalLog.java#L71)), whose `append` at [L586](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/LocalLog.java#L586) writes into the active segment, and whose `flush` at [L265](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/LocalLog.java#L265) fsyncs up to a given offset — this flush boundary is what the recovery-point checkpoint tracks.

Each segment pairs a data file with two sparse indexes. `LogSegment` ([class, L65](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/LogSegment.java#L65)) decides when to roll with `shouldRoll` ([L167](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/LogSegment.java#L167)) — segment bytes reached, time rolled over, or index full — and appends records at [L250](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/LogSegment.java#L250), indexing the first record's position per write call. The data file is `FileRecords` ([class, L45](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/common/record/internal/FileRecords.java#L45), note the new `record.internal` package) backed by a memory-mapped file; `append` at [L249](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/common/record/internal/FileRecords.java#L249) is just a write at the end, and `truncateTo` at [L321](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/common/record/internal/FileRecords.java#L321) is what makes unclean leader elections recoverable. `OffsetIndex` ([lookup, L97](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/OffsetIndex.java#L97)) maps relative offsets to file positions with binary search, and `TimeIndex` ([class, L54](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/TimeIndex.java#L54)) does the same for timestamps, enabling time-based retention and "read from yesterday 10:00" seeks. Idempotent and transactional producers are tracked by `ProducerStateManager` ([class, L70](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/ProducerStateManager.java#L70)), which persists sequence numbers as periodic snapshots ([loadSnapshots, L184](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/ProducerStateManager.java#L184)).

The high-watermark is the bridge between replication and visibility: `UnifiedLog.highWatermark` ([L506](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/UnifiedLog.java#L506)) reports the largest offset replicated to all in-sync replicas, and the log only exposes records below it to consumers. Log-end sits at [L2142](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/UnifiedLog.java#L2142); everything between watermark and log-end is written but not yet safe.

## Clients: Producers and Consumers

`KafkaProducer` ([class, L251](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/producer/KafkaProducer.java#L251)) is a bookkeeping front end for a background machine. Both `send` overloads ([L1027](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/producer/KafkaProducer.java#L1027) and [L1147](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/producer/KafkaProducer.java#L1147)) funnel into `doSend` ([L1180](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/producer/KafkaProducer.java#L1180)), which serializes the key and value, waits up to `max.block.ms` for partition metadata, and appends the record into a `ProducerBatch` via [tryAppend, L168](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/producer/internals/ProducerBatch.java#L168). Batching is the producer's main performance lever: `linger.ms` lets batches fill, `batch.size` caps them, and compression applies per batch. The `Sender` thread then drains and ships them, tracking in-flight batches for retries and sequencing.

`KafkaConsumer` ([class, L552](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/consumer/KafkaConsumer.java#L552)) is now a thin facade over two delegates. `subscribe` ([L725](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/consumer/KafkaConsumer.java#L725)) joins a group; `poll` ([L987](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/consumer/KafkaConsumer.java#L987)) simply forwards to whichever protocol you run. The classic delegate ([ClassicKafkaConsumer, L117](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/consumer/internals/ClassicKafkaConsumer.java#L117), poll at [L657](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/consumer/internals/ClassicKafkaConsumer.java#L657)) uses the long-standing group protocol with heartbeats on a background thread; the newer `AsyncKafkaConsumer` ([class, L178](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/consumer/internals/AsyncKafkaConsumer.java#L178), poll at [L936](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/consumer/internals/AsyncKafkaConsumer.java#L936)) implements the KIP-848 server-side rebalance protocol, moving most rebalance work out of a global lock. Both paths collect completed fetches into ordered records through `FetchCollector` ([class, L51](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/consumer/internals/FetchCollector.java#L51)) and talk to the broker via `ConsumerNetworkClient` ([send, L107](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/consumer/internals/ConsumerNetworkClient.java#L107)), which wraps the shared [NetworkClient, L89](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/NetworkClient.java#L89) — the same I/O core the producer uses, with `send` at [L616](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/NetworkClient.java#L616) and a completion `poll` at [L705](https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/NetworkClient.java#L705). If you have ever wired Kafka into an [Airflow](/airflow/) DAG, this split matters: the consumer's `poll` loop is where streaming and batch worlds hand off.

## Group Coordination: The New Java Runtime

Consumer groups have historically been managed by a Scala coordinator embedded in the broker. On trunk that logic lives in a dedicated `group-coordinator` module. `GroupCoordinatorService` ([class, L166](https://github.com/apache/kafka/blob/trunk/group-coordinator/src/main/java/org/apache/kafka/coordinator/group/GroupCoordinatorService.java#L166)) is the RPC surface — `joinGroup` at [L1009](https://github.com/apache/kafka/blob/trunk/group-coordinator/src/main/java/org/apache/kafka/coordinator/group/GroupCoordinatorService.java#L1009), `syncGroup` at [L1150](https://github.com/apache/kafka/blob/trunk/group-coordinator/src/main/java/org/apache/kafka/coordinator/group/GroupCoordinatorService.java#L1150), `heartbeat` at [L1193](https://github.com/apache/kafka/blob/trunk/group-coordinator/src/main/java/org/apache/kafka/coordinator/group/GroupCoordinatorService.java#L1193), and `commitOffsets` at [L2352](https://github.com/apache/kafka/blob/trunk/group-coordinator/src/main/java/org/apache/kafka/coordinator/group/GroupCoordinatorService.java#L2352) — all returning futures rather than blocking handler threads.

Internally the service routes each group to a shard keyed by the group's partition in the coordinator's log, and `GroupCoordinatorShard` ([class, L158](https://github.com/apache/kafka/blob/trunk/group-coordinator/src/main/java/org/apache/kafka/coordinator/group/GroupCoordinatorShard.java#L158)) is a deterministic state machine: membership changes and offset commits are first written as records, then applied to in-memory state, which makes group state reproducible after restarts — the same write-ahead-log philosophy as the log itself. Offset bookkeeping ends in `OffsetMetadataManager` ([class, L80](https://github.com/apache/kafka/blob/trunk/group-coordinator/src/main/java/org/apache/kafka/coordinator/group/OffsetMetadataManager.java#L80)), whose `commitOffset` at [L620](https://github.com/apache/kafka/blob/trunk/group-coordinator/src/main/java/org/apache/kafka/coordinator/group/OffsetMetadataManager.java#L620) produces the records that back the well-known `__consumer_offsets` topic.

## From Install to Your First Model

The README's quickstart path is KRaft-only — no ZooKeeper. To build from source, run `./gradlew jar`, then bootstrap a single-node cluster exactly as the README shows:

```bash
KAFKA_CLUSTER_ID="$(./bin/kafka-storage.sh random-uuid)"
./bin/kafka-storage.sh format --standalone -t $KAFKA_CLUSTER_ID -c config/server.properties
./bin/kafka-server-start.sh config/server.properties
```

That is a real KRaft controller and broker in one JVM: the storage tool stamps a cluster ID into the metadata log, and the server starts from `config/server.properties`. From there the official quickstart at kafka.apache.org/quickstart walks you through creating a topic with `bin/kafka-topics.sh` and exercising the round trip with the console producer and consumer — a two-minute verification before you write any code.

For an AI workload, the natural next step is making your first event a model-relevant one: emit inference requests as JSON keyed by user ID, append feature updates from your training jobs, or ship GPU telemetry from every node. A Python producer (`pip install kafka-python-ng` or `confluent-kafka`) needs only bootstrap servers and a topic name to start appending; the durable log means a consumer that crashes loses nothing, it just resumes from its last committed offset. That replay property is what makes Kafka a good complement to [Prometheus](/prometheus/) — metrics answer "how is the system now," while the log answers "give me every event since last Tuesday." And when the stream grows into a lake, the same events can be batch-drained to object storage or queried directly in ClickHouse for offline analysis.

## Honest Limits

Kafka is not a database: there are no secondary indexes, no queries, no per-key updates — the OffsetIndex exists to reach a position in a file, nothing more. Retention is a blunt instrument configured in `LogConfig` ([class, L65](https://github.com/apache/kafka/blob/trunk/storage/src/main/java/org/apache/kafka/storage/internals/log/LogConfig.java#L65)) — time- or size-based deletion of whole segments — so random access to old records is what compaction and external stores are for. Ordering is guaranteed only within a partition; choosing a good partition key for your events is a real design decision, and rekeying after the fact is painful. A broker JVM with modest defaults is fine to start with, but cross-AZ replication traffic, segment fsync tuning, and partition counts that now also drive KRaft metadata size all need attention as throughput grows.

The codebase itself carries its own friction: the ongoing migration from Scala core to Java modules means related logic is split across `core`, `storage`, and `group-coordinator` (the Scala LogManager even aliases the Java one), and two live consumer protocols mean any client-behavior reading must check which delegate is actually running. None of that diminishes the engineering here — it is just the price of a system that has been evolving this fast for this long, and reading the sources on trunk, as we did here, is the most reliable way to know what your cluster is really doing.
