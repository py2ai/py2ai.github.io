pandas has a scaling problem that every data scientist eventually hits: it is single-threaded, and the moment your dataset outgrows a fraction of your machine's memory, workflows that felt snappy on a laptop become slow, swap-thrashing misery. [Modin](https://github.com/modin-project/modin) is a drop-in replacement for pandas built by the team behind some serious Berkeley dataframe research. Its promise, straight from the README: "Scale your pandas workflows by changing one line of code." You swap `import pandas as pd` for `import modin.pandas as pd`, and Modin transparently spreads the data and the computation across every core you own — or across a whole cluster.

What makes Modin worth a source tour is not just the promise but the engineering discipline behind it. Instead of reimplementing pandas, Modin wraps it: each `modin.pandas.DataFrame` holds a *query compiler* that describes operations symbolically, and each query compiler points at a *partitioned dataframe* whose grid cells are chunks of your data sitting in a distributed engine like Ray or Dask. The architecture is deliberately modular so new engines and storage formats can be plugged in as they mature.

In this tour we walk the `main` branch of `modin-project/modin` from the import statement down to the Ray tasks that move your partitions around. Two diagrams anchor the walk: a compact overview of the layers, and a detail map of the classes that make the layers talk to each other. Every class name and line number below was verified directly against the tree.

Reading the overview from left to right:

- `import modin.pandas as pd` lands in [modin/pandas/__init__.py](https://github.com/modin-project/modin/blob/main/modin/pandas/__init__.py#L159), which re-exports [DataFrame](https://github.com/modin-project/modin/blob/main/modin/pandas/dataframe.py#L101) and [Series](https://github.com/modin-project/modin/blob/main/modin/pandas/series.py#L87). Engine boot is lazy: [_initialize_engine, L121](https://github.com/modin-project/modin/blob/main/modin/pandas/__init__.py#L121) only starts Ray or Dask on first real use.
- [read_csv, L168](https://github.com/modin-project/modin/blob/main/modin/pandas/io.py#L168) and [from_pandas, L1008](https://github.com/modin-project/modin/blob/main/modin/pandas/io.py#L1008) in `modin/pandas/io.py` are the two front doors for data. Neither parses anything itself — both [delegate to FactoryDispatcher](https://github.com/modin-project/modin/blob/main/modin/pandas/io.py#L1024).
- [FactoryDispatcher, L104](https://github.com/modin-project/modin/blob/main/modin/core/execution/dispatching/factories/dispatcher.py#L104) is the traffic controller. It subscribes to config changes and routes every I/O and conversion call — see its [from_pandas, L188](https://github.com/modin-project/modin/blob/main/modin/core/execution/dispatching/factories/dispatcher.py#L188) and [read_csv, L250](https://github.com/modin-project/modin/blob/main/modin/core/execution/dispatching/factories/dispatcher.py#L250).
- Which factory is active is decided by [Engine, L195](https://github.com/modin-project/modin/blob/main/modin/config/envvars.py#L195) and [Backend, L401](https://github.com/modin-project/modin/blob/main/modin/config/envvars.py#L401) in `modin/config/envvars.py` — environment-variable-backed settings, with [NPartitions, L837](https://github.com/modin-project/modin/blob/main/modin/config/envvars.py#L837) controlling how many chunks your data is split into.
- [BaseFactory, L133](https://github.com/modin-project/modin/blob/main/modin/core/execution/dispatching/factories/factories.py#L133) encodes the naming convention: a factory is called `{StorageFormat}On{Engine}Factory`. The dispatcher literally concatenates strings like `PandasOnRayFactory` ([L752](https://github.com/modin-project/modin/blob/main/modin/core/execution/dispatching/factories/factories.py#L752)) or `PandasOnDaskFactory` ([L776](https://github.com/modin-project/modin/blob/main/modin/core/execution/dispatching/factories/factories.py#L776)) and looks them up.
- The factory's `prepare()` method binds an I/O class: PandasOnRayFactory sets `io_cls` to [PandasOnRayIO, L68](https://github.com/modin-project/modin/blob/main/modin/core/execution/ray/implementations/pandas_on_ray/io/io.py#L68), which wires together the frame class, partition class, and query compiler class for the Ray stack.
- Everything comes back to the API as a [PandasQueryCompiler, L279](https://github.com/modin-project/modin/blob/main/modin/core/storage_formats/pandas/query_compiler.py#L279) — an engine-agnostic description of your operations ([groupby_agg, L4236](https://github.com/modin-project/modin/blob/main/modin/core/storage_formats/pandas/query_compiler.py#L4236) is a good example of one operator entry point).
- The compiler wraps a [PandasDataframe, L82](https://github.com/modin-project/modin/blob/main/modin/core/dataframe/pandas/dataframe/dataframe.py#L82), the partition-grid metadata object. Its [apply_full_axis, L2956](https://github.com/modin-project/modin/blob/main/modin/core/dataframe/pandas/dataframe/dataframe.py#L2956) is the workhorse that maps a pandas function across whole rows or columns.
- Finally, each grid cell is a [PandasOnRayDataframePartition, L35](https://github.com/modin-project/modin/blob/main/modin/core/execution/ray/implementations/pandas_on_ray/partitioning/partition.py#L35) holding a Ray object reference; its [apply, L99](https://github.com/modin-project/modin/blob/main/modin/core/execution/ray/implementations/pandas_on_ray/partitioning/partition.py#L99) launches the actual remote pandas work.

## One Dispatch Layer to Rule Them All

The neatest trick in the codebase is how little the dispatch layer knows about engines. `FactoryDispatcher` never imports Ray or Dask directly. It calls [_get_prepared_factory_for_backend, L129](https://github.com/modin-project/modin/blob/main/modin/core/execution/dispatching/factories/dispatcher.py#L129), which formats the string `f"{execution.storage_format}On{execution.engine}Factory"` and resolves it with `getattr` against the factories module. Adding a new execution engine is therefore mostly a matter of adding a class that follows the naming convention and implements `prepare()` — the dispatcher picks it up automatically.

The same pattern repeats in the I/O stack. [BaseIO, L48](https://github.com/modin-project/modin/blob/main/modin/core/io/io.py#L48) defines the reader/writer contract, and its [from_pandas, L99](https://github.com/modin-project/modin/blob/main/modin/core/io/io.py#L99) builds a query compiler around whatever `frame_cls` the concrete engine binds. Engine-specific I/O classes then compose readers from mixins: PandasOnRayIO assembles its parallel `read_csv` from a Ray wrapper, a pandas CSV parser, and the [CSVDispatcher, L19](https://github.com/modin-project/modin/blob/main/modin/core/io/text/csv_dispatcher.py#L19), which knows how to split a text file into chunks that become partitions. It is dependency injection by class composition, done without any framework.

## The Query Compiler Boundary

`modin.pandas.DataFrame` is intentionally thin. Look at [its __init__, L147](https://github.com/modin-project/modin/blob/main/modin/pandas/dataframe.py#L147): the constructor mostly decides which query compiler to hold, and when you hand it an eager pandas DataFrame it immediately converts via [from_pandas, L266](https://github.com/modin-project/modin/blob/main/modin/pandas/dataframe.py#L266). Every public method either translates into a query-compiler call or falls back.

That fallback path matters. [BaseQueryCompiler.default_to_pandas, L290](https://github.com/modin-project/modin/blob/main/modin/core/storage_formats/base/query_compiler.py#L290) materializes the whole frame locally and runs the plain pandas implementation. This is how Modin reaches 90.8% DataFrame and 88.05% Series API coverage (per the README's coverage table) without implementing every edge case in a distributed fashion: rarely-used methods still *work*, they just give up parallelism. Group-by, by contrast, gets first-class treatment through [groupby_agg, L4236](https://github.com/modin-project/modin/blob/main/modin/core/storage_formats/pandas/query_compiler.py#L4236) in the pandas storage format's query compiler, and the user-facing [DataFrameGroupBy, L112](https://github.com/modin-project/modin/blob/main/modin/pandas/groupby.py#L112) keeps arguments compatible across installed pandas versions through the caster machinery in `modin/core/storage_formats/pandas/query_compiler_caster.py`.

## The Partition Grid and Ray Tasks

Under the query compiler sits the physical model. A `PandasDataframe` is an `m x n` grid of partition objects plus cached index/column metadata. Row- and column-wise operations either shuffle the grid or map functions over it. The engine-agnostic [PandasDataframePartitionManager, L95](https://github.com/modin-project/modin/blob/main/modin/core/dataframe/pandas/partitioning/partition_manager.py#L95) handles layout, while Ray-specific subclasses like [PandasOnRayDataframePartitionManager, L35](https://github.com/modin-project/modin/blob/main/modin/core/execution/ray/implementations/pandas_on_ray/partitioning/partition_manager.py#L35) decide how to submit work.

For whole-axis operations, partitions can be fused into virtual axis partitions — [PandasOnRayDataframeVirtualPartition, L30](https://github.com/modin-project/modin/blob/main/modin/core/execution/ray/implementations/pandas_on_ray/partitioning/virtual_partition.py#L30), with column and row variants — so a function sees one large chunk instead of many small ones, cutting task overhead. Each physical partition wraps exactly one Ray `ObjectRef`. When you call `.apply()`, Modin submits a remote task that deserializes the chunk, runs your pandas code, and returns a new object reference. The engine boots lazily on first use: [initialize_ray, L55](https://github.com/modin-project/modin/blob/main/modin/core/execution/ray/common/utils.py#L55) creates a local Ray cluster sized from your CPU count. In local mode the README is explicit that Modin "will create and manage a local (Dask or Ray) cluster for the execution" — you never touch the scheduler yourself.

What the detail diagram makes obvious is symmetry. The Dask column mirrors the Ray column class-for-class: [PandasOnDaskDataframe, L22](https://github.com/modin-project/modin/blob/main/modin/core/execution/dask/implementations/pandas_on_dask/dataframe/dataframe.py#L22), its partition manager at [L28](https://github.com/modin-project/modin/blob/main/modin/core/execution/dask/implementations/pandas_on_dask/partitioning/partition_manager.py#L28), and a partition wrapping a Dask future at [L26](https://github.com/modin-project/modin/blob/main/modin/core/execution/dask/implementations/pandas_on_dask/partitioning/partition.py#L26). Your code never changes between the two engines; only the grid cells' payloads differ — object references versus futures.

## From Install to Your First Model

Everything above is invisible to you on purpose. Here is the whole onboarding, using only what the README documents:

```bash
pip install "modin[all]"        # Modin with Ray and Dask engines
# or: pip install "modin[ray]"  /  pip install "modin[dask]"
```

Modin auto-detects which engine you have installed, or you can pin one with the `MODIN_ENGINE` environment variable (`ray`, `dask`, or `unidist`). Then the famous one-line migration:

```python
import modin.pandas as pd       # was: import pandas as pd

df = pd.read_csv("my_dataset.csv")   # parsed in parallel across your cores
daily = df.groupby("date").sum()     # distributed group-by aggregation
```

That `groupby` call executes as a distributed aggregation over partition chunks — no code changes relative to pandas. From there, getting data ready for a first model is ordinary again, because Modin exposes the pandas API you know:

```python
import numpy as np

features = df[["sqft", "rooms"]].to_numpy()   # verified: to_numpy in modin/pandas/base.py
target = np.log1p(df["price"].to_numpy())
w, *_ = np.linalg.lstsq(features, target, rcond=None)   # your first (tiny) model
```

The NumPy hand-off happens through verified public methods (`to_numpy`, `values`), so any estimator library that consumes arrays — scikit-learn, XGBoost, whatever you already use with pandas — slots in unchanged. If you want a cluster later, the same script runs on Ray or Dask clusters; Modin's [out-of-core docs](https://modin.readthedocs.io/en/latest/getting_started/why_modin/out_of_core.html) cover datasets bigger than memory.

## Honest Limits

- **Not a 100% drop-in.** The README's own coverage table lists `pd.DataFrame` at 90.8% and `pd.Series` at 88.05% across engines. Missing methods usually exist via `default_to_pandas`, but some, like `read_json`, are marked partial with a link to open issue #554.
- **Small data can be slower.** Partitioning and task submission have overhead. The README claims speed-ups of "up to 4x on a laptop with 4 physical cores" for larger workloads — that is the verified claim, and it does not translate to tiny frames where pandas wins.
- **Engine switching is one-way.** The README warns not to change the engine after your first Modin operation, as it "will result in undefined behavior." Set `MODIN_ENGINE` before importing.
- **Ray defaults are leaner.** Since Modin 0.30.0, installs use `ray` (not `ray[default]`), so the dashboard and cluster launcher are not included by default.
- **Serial operations stay serial.** Anything that funnels through `default_to_pandas` materializes a local copy; there is no magic parallelism for unimplemented APIs.

## Where Modin Fits in Your Toolbox

Modin is the "keep my pandas muscle memory" answer to scaling. If you are willing to rewrite against a new API, [Polars](/polars/) offers a Rust-native query engine with its own expression syntax; if you want SQL-first analytics, [DuckDB](/duckdb/) is excellent; and for columnar interchange between tools, [Arrow](/arrow/) is the substrate several of these systems share. Modin's niche is the pandas code you already have — notebooks, features scripts, team-internal tooling — that must simply handle more data. For multi-machine dataframe processing with the same API, [Dask's](/dask/) dataframe is the closest alternative, and thanks to Modin's dispatcher design it is also the engine sitting one environment variable away. And when your work is numpy-shaped rather than dataframe-shaped, our [NumPy](/numpy/) tour covers the array side of the ecosystem.

The takeaway from the source: Modin's power comes from three honest abstractions — a pandas-lookalike API, an engine-agnostic query compiler, and a partition grid with pluggable executors. Change one import, and the layers below quietly swap from your CPU's single thread to every core you can rent.
