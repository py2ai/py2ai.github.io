TensorFlow Serving is Google's open-source model server: the piece of infrastructure that takes a trained TensorFlow model off a researcher's laptop and makes it answer real network traffic, reliably, at low latency. You export a SavedModel into a versioned directory, point the server at the parent folder, and it discovers every numbered version, loads the newest one, swaps versions atomically while old requests drain, and answers `Predict`, `Classify`, `Regress`, and `GetModelMetadata` calls over both gRPC and an HTTP/REST endpoint. It ships as a single prebuilt binary, `tensorflow_model_server`, published through apt packages and Docker images, and it has quietly run a large share of Google's internal inference traffic for years.

Why bother reading its source at all? Because this is one of the few production-grade serving systems written almost entirely in C++, and the code is organized around a small set of interfaces — `Source`, `SourceAdapter`, `Loader`, `Manager` — that compose into a genuinely elegant component model. Once you see how those pieces snap together, you understand not just this server but the general anatomy of every model server you will ever touch. It also makes a sharp contrast with the Python-centric stacks we have covered before, like [TorchServe](/torchserve/), and with the multi-framework [Triton Server](/triton-server/), both of which lean on Python or backend-specific runtimes where TensorFlow Serving compiles everything down to one C++ process.

This post is a source tour, not a tutorial. Every symbol below links to a real file and line on the `master` branch, and the two architecture diagrams were generated directly from the actual repository tree. We will follow the server from `main()` all the way to a batched session execution, then close with the practical bits — installation, first model, and the limits you will hit in production.

## What the Server Must Solve

Before diving into files, it helps to enumerate the problems a model server has to solve, because every directory in the repository maps to one of them. First, discovery: new model versions appear on disk (or on GCS or S3) while the server is running, and something must notice. Second, versioning policy: when version 7 shows up while version 6 still serves traffic, the server needs rules for when to load 7, when to unload 6, and what to do if loading 7 fails. Third, loading itself: a SavedModel must be deserialized into a session with its graph, signature definitions, and variables, and that load can take minutes for large models. Fourth, efficiency: single requests are wasteful for GPUs, so the server can coalesce concurrent requests into batches. Fifth, presentation: gRPC, REST, health checks, and monitoring endpoints all need to expose the same underlying manager state.

The repository layout mirrors this list almost exactly. `tensorflow_serving/sources/` contains things that watch the outside world, `tensorflow_serving/core/` contains the version-management machinery, `tensorflow_serving/servables/tensorflow/` knows how to turn a SavedModel into something callable, `tensorflow_serving/batching/` implements request coalescing, and `tensorflow_serving/model_servers/` glues everything into the binary you actually run. That symmetry between problem and directory is the first sign of a well-factored codebase, and it is what makes the diagrams below readable.

## Reading the overview from left to right:

- [main, L82](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/main.cc#L82) is where the binary starts. It declares roughly forty command-line flags — port, `model_base_path`, batching parameters, session parallelism — into an Options struct and hands it to the server builder at [main, L342](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/main.cc#L342).
- [Server::BuildAndStart, L182](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/server.cc#L182) creates the `ServerCore`, registers the gRPC services, optionally starts the REST frontend, and then blocks in [WaitForTermination, L464](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/server.cc#L464) until shutdown.
- [ServerCore::Create, L260](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/server_core.cc#L260) is the true orchestrator. Its [Initialize, L306](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/server_core.cc#L306) method builds the three moving parts — source, adapters, manager — and [WaitUntilModelsAvailable, L328](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/server_core.cc#L328) keeps startup blocked until every configured model is actually servable.
- On the discovery side, [FileSystemStoragePathSource::Create, L373](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/sources/storage_path/file_system_storage_path_source.cc#L373) starts a polling thread; [PollFileSystemForConfig, L329](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/sources/storage_path/file_system_storage_path_source.cc#L329) scans each base path for numerically named subdirectories, and [PollFileSystemAndInvokeCallback, L444](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/sources/storage_path/file_system_storage_path_source.cc#L444) pushes the result as aspired versions.
- [SavedModelBundleSourceAdapter::Create, L36](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/servables/tensorflow/saved_model_bundle_source_adapter.cc#L36) builds the adapter that converts each aspired storage path into a loadable servable, wiring the adapter chain the core requested in [CreateAdapters, L728](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/server_core.cc#L728).
- [SavedModelBundleFactory::CreateSavedModelBundle, L116](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/servables/tensorflow/saved_model_bundle_factory.cc#L116) does the heavy lifting: it loads the meta-graph, session, and signature map, then optionally replays recorded traffic via [RunSavedModelWarmup, L82](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/servables/tensorflow/saved_model_warmup.cc#L82) so the first real request is not slow.
- On the management side, [ServerCore::CreateAspiredVersionsManager, L785](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/server_core.cc#L785) builds the [AspiredVersionsManager, L85](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/aspired_versions_manager.h#L85), the state machine that owns every loaded and loading servable in the process.
- That manager orders candidates with a pluggable policy — the model server default is [AvailabilityPreservingPolicy, L39](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/availability_preserving_policy.h#L39), which never unloads the currently serving version until its successor is fully ready.
- Finally, the request path: [PredictionServiceImpl::Predict, L38](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/prediction_service_impl.cc#L38) receives the gRPC call, acquires a scoped [ServableHandle, L75](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/servable_handle.h#L75) through [Manager::GetUntypedServableHandle, L109](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/manager.h#L109), and executes the signature via the predictor in [TensorflowPredictor::Predict, L33](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/servables/tensorflow/predict_impl.cc#L33).

## Inside the Loading Flow

The overview deliberately hides the most interesting machinery: what exactly happens between "a new version directory appeared" and "requests now flow to it". The detail diagram expands that seam, and it is where the design earns its reputation.

<div style="overflow-x:auto;"><img src="https://pyshine.com/assets/img/diagrams/tensorflow-serving/tensorflow-tensorflow-serving-architecture.svg" alt="TensorFlow Serving detailed loading flow" style="max-width:100%;"></div>
<p><em>The detailed view: adapter wiring, the manager and its policies, per-servable harnesses, state monitoring, and the batching layer wrapped around the session.</em></p>

Start with the adapter contract. Everything that feeds models into the manager is a [Source, L65](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/source.h#L65) — a thing that pushes aspired versions to a callback. A [SourceAdapter, L60](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/source_adapter.h#L60) is a source that transforms another source's output, and the storage-path-to-SavedModel chain is exactly two such hops: the file system source emits `StoragePath` items, an adapter turns them into loadable servables. [ServerCore::CreateRouter, L696](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/server_core.cc#L696) inserts a dynamic router between them so each model name reaches only its own adapter.

Inside the manager, every candidate version is wrapped in a [LoaderHarness, L52](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/loader_harness.h#L52), a tiny state machine that moves each servable through new, loading, ready, and unloading states while guarding transitions against races. The harness drives a [Loader, L57](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/loader.h#L57), whose `Load()` at [Load, L90](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/loader.h#L90) materializes the model. Crucially, `Loader::EstimateResources()` lets the manager decide whether the new version even fits before starting the load; the estimate comes from [EstimateResourceFromPath, L92](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/servables/tensorflow/bundle_factory_util.cc#L92) in the SavedModel case. [BasicManager, L106](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/basic_manager.h#L106) implements the thread pools and retry logic behind [AspiredVersionsManager, L85](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/aspired_versions_manager.h#L85), and both report every state change to a [ServableStateMonitor, L46](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/servable_state_monitor.h#L46), which is what powers the model-status API implemented in [GetModelStatusImpl::GetModelStatus, L66](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/get_model_status_impl.cc#L66).

The batching layer is similarly clean. When you pass `--enable_batching`, the factory does not wrap the raw session; it wraps it once at load time using [WrapSessionForBatching, L100](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/servables/tensorflow/bundle_factory_util.cc#L100), so every request for that model transparently goes through [BatchingSession](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/batching/batching_session.cc#L160). That class queues incoming runs into a [StreamingBatchScheduler, L114](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/batching/streaming_batch_scheduler.h#L114), merges tensors with the padding helpers in `batching_util`, executes one combined `Session::Run`, then splits outputs back per request in [ProcessBatch, L717](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/batching/batching_session.cc#L717). Because batching is a session decorator rather than a server feature, it composes with any platform that exposes a session-shaped interface.

Step back and the pattern across all of this is dependency injection with interfaces, done the C++ way: sources produce, adapters transform, loaders own, and the manager schedules. No component above knows about HTTP or protobufs, which is why the same core has survived years of runtime churn underneath it. When you next evaluate a serving system, ask whether it can express "keep serving 6 until 7 is ready, but never if both cannot fit in memory" as a first-class rule — here it is roughly one policy class plus one estimate function.

## From Install to Your First Model

The fastest path is Docker: `docker pull tensorflow/serving`, then run the container with `--model_base_path=/models/my_model` mounted from the host. The image listens on 8500 for gRPC and 8501 for REST by default. If you prefer packages on Ubuntu, a one-line `apt-get install tensorflow-model-server` from the project's repository works, and a plain `pip install tensorflow-serving-api` gives you the generated Python clients for both APIs.

Preparing a model means exporting a SavedModel with a numbered version directory: `/models/my_model/123/` containing `saved_model.pb` and a `variables/` folder. Point `--model_base_path` at `/models/my_model` — the parent, never the version directory — and the server picks the highest number by default. Restarting to deploy is optional: with `--model_config_file` you can serve many models from one process, and with `--model_config_file_poll_wait_seconds` the server re-reads that config periodically, so adding a model is a file edit rather than a restart.

Two flags are worth enabling on day one. `--enable_batching` activates the batching session described above, tunable through `--batching_parameters_file` where you set max batch size, timeout in microseconds, and the number of threads; without it, every request runs alone. `--enable_model_warmup` triggers the warmup replay so lazy initializations happen during load instead of on your first customer request. For an HTTP smoke test, `curl -d '{"instances":[[1.0,2.0,5.0]]}' -X POST http://localhost:8501/v1/models/my_model:predict` is usually the first thing people run — note the REST handler behind that URL lives in [HttpRestApiHandler, L56](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/model_servers/http_rest_api_handler.cc#L56), dispatched by the embedded server in `http_server.cc`. For training the model you will deploy, our earlier [TensorFlow](/tensorflow/) overview covers the export side, and if you need to serve non-TensorFlow formats, the adapters in this repository stop at TF-style inputs — that is where the alternatives come in.

## Honest Limits

TensorFlow Serving is battle-tested, but it is opinionated, and several of its opinions will cost you. The biggest one: it serves TensorFlow formats. A PyTorch or ONNX artifact must be converted first, and some conversions are lossy; if your stack is not TensorFlow-native, [Triton Server](/triton-server/) or [TorchServe](/torchserve/) will save you a translation layer. Second, the served-model surface is static by design — the binary serves a configured set of models and version directories, and there is no built-in dynamic model registry, no authentication layer, and no rate limiting. You are expected to put a proxy in front and handle auth outside the process.

Third, memory behavior during swaps deserves respect. With the default availability-preserving policy, old and new versions coexist in RAM until the new one is warm, so a redeploy of a 30 GB model briefly needs twice that; the alternative [ResourcePreservingPolicy, L42](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/core/resource_preserving_policy.h#L42) unloads first but risks a serving gap. Fourth, batching defaults are conservative and single-model scoped; per-model tuning requires either the config file or the newer per-model `batching_params.pbtxt` dropped into the SavedModel directory. Fifth, contributing is not casual: the build is Bazel, the tests are extensive, and the abstractions are template-heavy C++, so most teams treat the binary as a product rather than a library. None of these are disqualifying — they are the price of a server that has handled production inference at enormous scale for most of a decade. Read the interfaces once, and every flag in `main.cc` becomes an obvious knob.
