Text-to-speech is the rare field where the whole lineage of a decade still runs side by side: attention-based seq2seq models from 2017, flow-based generators from 2020, adversarial end-to-end systems, and the GPT-style voice cloners of the streaming era. The Coqui toolkit is the single place where all of them ship in one `pip install TTS`, with pretrained checkpoints for over a thousand languages via the Fairseq-MMS integration. The repo is `coqui-ai/TTS`, MPL-2.0 licensed, and its Python package is a directory literally called `TTS/` — a few hundred files that separate cleanly into a public facade, an orchestration layer, a shelf of model wrappers, their neural internals, a vocoder shelf, and a set of command-line entry points. In this tour we read those layers against the `dev` branch as it exists in the repository today, file by file, symbol by symbol. As always in this series, what follows is an educational walkthrough of published source code.

The facade is one class. [TTS, L15](https://github.com/coqui-ai/TTS/blob/dev/TTS/api.py#L15) in `TTS/api.py` is what every tutorial teaches: construct it with a zoo name like `tts_models/en/ljspeech/vits`, call `tts()` for a waveform or `tts_to_file()` for a wav on disk. Underneath, a `ModelManager` resolves names against a JSON registry and downloads checkpoints with MD5 verification, a `Synthesizer` loads config, acoustic model, and vocoder into one inference unit, and the model wrappers themselves delegate to per-architecture neural layers — flow blocks, GPT transformers, diffusion decoders — that live in `TTS/tts/layers/`. It is a textbook example of an SDK that hides a zoo behind one import, comparable in spirit to how [Piper](/piper/) packages a single fast model, except here the package is the entire museum.

The map below shows the five layers: the facade (`api.py` and the `tts` CLI), the orchestration pair (`ModelManager` and `Synthesizer`), the acoustic zoo on its shared base, the vocoder shelf, and the text/audio utilities that glue everything together.

Reading the overview from left to right:

- [TTS, L15](https://github.com/coqui-ai/TTS/blob/dev/TTS/api.py#L15) is the public class; its [tts(), L237](https://github.com/coqui-ai/TTS/blob/dev/TTS/api.py#L237) validates arguments and forwards to the synthesizer.
- [ModelManager, L30](https://github.com/coqui-ai/TTS/blob/dev/TTS/utils/manage.py#L30) owns the zoo registry; [download_model, L371](https://github.com/coqui-ai/TTS/blob/dev/TTS/utils/manage.py#L371) caches files with MD5 checks.
- [Synthesizer, L25](https://github.com/coqui-ai/TTS/blob/dev/TTS/utils/synthesizer.py#L25) is the inference engine; its [tts(), L257](https://github.com/coqui-ai/TTS/blob/dev/TTS/utils/synthesizer.py#L257) splits sentences, runs the model, and stitches waveforms.
- [BaseTTS, L24](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/base_tts.py#L24) is the shared skeleton every acoustic wrapper inherits.
- [Vits, L603](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/vits.py#L603) is the end-to-end adversarial workhorse; [inference, L1089](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/vits.py#L1089) samples stochastic durations.
- [Xtts, L191](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/xtts.py#L191) clones a voice from seconds of reference audio; [inference, L503](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/xtts.py#L503) exposes temperature, top-k, and top-p like an LLM.
- [GAN, L21](https://github.com/coqui-ai/TTS/blob/dev/TTS/vocoder/models/gan.py#L21) is the vocoder framework that pairs generators with discriminators.
- [TTSTokenizer, L10](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/utils/text/tokenizer.py#L10) and [AudioProcessor, L32](https://github.com/coqui-ai/TTS/blob/dev/TTS/utils/audio/processor.py#L32) bracket the flow: text to ids on the way in, mels and wavs on the way out.

## Why You Need This

Because the facade is a masterclass in API design over heterogeneous models. The constructor accepts either a zoo name or raw paths — [load_tts_model_by_name, L159](https://github.com/coqui-ai/TTS/blob/dev/TTS/api.py#L159) for the registry route, [load_tts_model_by_path, L190](https://github.com/coqui-ai/TTS/blob/dev/TTS/api.py#L190) for your own checkpoints — and after loading, the object introspects itself: `is_multi_speaker` and `is_multi_lingual` properties probe the loaded model, and `tts.speakers` lists the voices a checkpoint knows. Argument hygiene lives in [_check_arguments, L215](https://github.com/coqui-ai/TTS/blob/dev/TTS/api.py#L215), which refuses to run a multi-speaker model without a speaker, or to pass an `emotion` to anything but the retired Coqui Studio cloud models — the error message at [L235](https://github.com/coqui-ai/TTS/blob/dev/TTS/api.py#L235) states bluntly that those are discontinued, a rare case of an SDK announcing its own sunset in a ValueError.

The same facade also covers voice conversion. [load_vc_model_by_name, L148](https://github.com/coqui-ai/TTS/blob/dev/TTS/api.py#L148) builds a second Synthesizer configured as a converter and loads [FreeVC, L298](https://github.com/coqui-ai/TTS/blob/dev/TTS/vc/models/freevc.py#L298), so one API surface spans synthesis and re-voicing. And the zoo breadth is real: beyond the headline models there is [GlowTTS, L22](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/glow_tts.py#L22), Bark for unconstrained cloning, and roughly eleven hundred Fairseq-MMS voices reachable by the same naming scheme. If your benchmark is "how much of neural TTS can I reach from one import," nothing else comes close.

## From Install to Your First Model

The command line is a thin wedge into the same layers. The `tts` shell command is implemented by [synthesize.py](https://github.com/coqui-ai/TTS/blob/dev/TTS/bin/synthesize.py), whose giant docstring at [L12](https://github.com/coqui-ai/TTS/blob/dev/TTS/bin/synthesize.py#L12) doubles as the man page: `tts --list_models` prints the zoo, `--model_name tts_models/de/thorsten/tacotron2-DDC` picks a voice, `--text` supplies input. The [main, L144](https://github.com/coqui-ai/TTS/blob/dev/TTS/bin/synthesize.py#L144) function imports `TTS.api`, `ModelManager`, and `Synthesizer` lazily at [L338](https://github.com/coqui-ai/TTS/blob/dev/TTS/bin/synthesize.py#L338), then builds the synthesizer directly at [L423](https://github.com/coqui-ai/TTS/blob/dev/TTS/bin/synthesize.py#L423) — the CLI deliberately bypasses the `TTS` class to avoid one import layer, which is a nice touch worth copying in your own tools.

The download side is worth reading because it shows what a model zoo actually is: a JSON file plus caching discipline. Model names follow `type/language/dataset/model` as documented on [L372](https://github.com/coqui-ai/TTS/blob/dev/TTS/utils/manage.py#L372), and [download_model, L371](https://github.com/coqui-ai/TTS/blob/dev/TTS/utils/manage.py#L371) checks a stored `hash.md5` against the expected checksum at [L389](https://github.com/coqui-ai/TTS/blob/dev/TTS/utils/manage.py#L389) before trusting its cache — corrupted or updated checkpoints are silently re-fetched. For serving, `TTS/server/server.py` builds a module-level [Synthesizer, L104](https://github.com/coqui-ai/TTS/blob/dev/TTS/server/server.py#L104) and exposes a Flask route at [L189](https://github.com/coqui-ai/TTS/blob/dev/TTS/server/server.py#L189) whose handler [tts, L190](https://github.com/coqui-ai/TTS/blob/dev/TTS/server/server.py#L190) synthesizes, writes to an in-memory buffer, and returns it with an `audio/wav` mimetype; there is even a MaryTTS compatibility endpoint at [L237](https://github.com/coqui-ai/TTS/blob/dev/TTS/server/server.py#L237) so legacy clients keep working.

Training has its own entry point. [train_tts.py](https://github.com/coqui-ai/TTS/blob/dev/TTS/bin/train_tts.py) starts at [main, L16](https://github.com/coqui-ai/TTS/blob/dev/TTS/bin/train_tts.py#L16), loads and registers a config through `TTS.config`, loads dataset samples through `TTS.tts.datasets`, and hands the pair to [setup_model, L6](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/__init__.py#L6), a factory that maps a config class to its wrapper. The outer loop, though, is not in this repo at all: the file imports `Trainer` and `TrainerArgs` from a separate `trainer` package at [L4](https://github.com/coqui-ai/TTS/blob/dev/TTS/bin/train_tts.py#L4) and constructs it at [L58](https://github.com/coqui-ai/TTS/blob/dev/TTS/bin/train_tts.py#L58). The training loop lives in a sibling repository; this one owns models, data, and configs — for instance [VitsConfig, L9](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/configs/vits_config.py#L9) — and the glue between them.

## The Model Zoo's Two Generations

Every wrapper inherits one of two base classes, and the split is the history of the field in inheritance form. The first generation shares [BaseTTS, L24](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/base_tts.py#L24), which owns batch formatting, sequence sorting, and the `format_batch` contract that data loaders satisfy. On it sit the spectrogram-predictors: [Tacotron2, L21](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/tacotron2.py#L21) with its autoregressive decoder and attention ([inference, L239](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/tacotron2.py#L239)), the flow-based GlowTTS, and [ForwardTTS, L172](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/forward_tts.py#L172), the shared implementation behind the FastSpeech and FastPitch configs where an alignment module predicts durations in one parallel pass.

The second generation hangs off [BaseTTSE2E, L444](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/base_tts.py#L444) in the same file: end-to-end models that emit audio directly and speak like language models. [Tortoise, L309](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/tortoise.py#L309) is the research-grade cloner — it extracts voice conditionings via [get_conditioning_latents, L405](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/tortoise.py#L405), generates multiple candidates in [synthesize, L500](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/tortoise.py#L500), and reranks them in [inference, L598](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/tortoise.py#L598). Between the two generations sits VITS at two thousand lines: [VitsDataset, L256](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/vits.py#L256) and [VitsArgs, L366](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/vits.py#L366) define its data and options, and [forward, L961](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/vits.py#L961) implements the training step where alignment, duration, and waveform are learned jointly.

## Inside the Engines: VITS and XTTS

The detail map zooms into the neural internals, and VITS is the best place to see how deep the layering goes. The wrapper delegates to `TTS/tts/layers/vits/`: [TextEncoder, L29](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/layers/vits/networks.py#L29) embeds phonemes, [PosteriorEncoder, L235](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/layers/vits/networks.py#L235) compresses real audio during training, and the normalizing-flow blocks (a `ResidualCouplingBlocks` stack at [L169](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/layers/vits/networks.py#L169)) map between latent distributions. Durations come from [StochasticDurationPredictor, L150](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/layers/vits/stochastic_duration_predictor.py#L150), and the monotonic alignment search that stabilizes training is a Cython kernel — `TTS/tts/utils/monotonic_align/core.pyx` — reached through `maximum_path` in `TTS/tts/utils/helpers.py`, which VITS imports at [L29](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/vits.py#L29).

XTTS is the modern chapter and reads like an LLM wearing a vocoder. [Xtts, L191](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/xtts.py#L191) assembles pieces from `TTS/tts/layers/xtts/`: a [DiscreteVAE, L201](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/layers/xtts/dvae.py#L201) that compresses audio into discrete tokens, the [GPT, L88](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/layers/xtts/gpt.py#L88) transformer that autoregressively generates those tokens from text plus a six-second voice sample, and [HifiDecoder, L615](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/layers/xtts/hifigan_decoder.py#L615) that renders the result to waveform. Its [inference, L503](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/models/xtts.py#L503) signature is pure generation vocabulary — `temperature=0.75`, `top_k=50`, `top_p=0.85`, `repetition_penalty` — and streaming works by hot-swapping HuggingFace generation internals: `init_stream_support` at [L881](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/layers/xtts/stream_generator.py#L881) monkey-patches the generation mixin so tokens stream out as they are sampled. Tortoise, the older cloner, uses the same pattern with different parts: a `UnifiedVoice` transformer at [L262](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/layers/tortoise/autoregressive.py#L262), the diffusion decoder at [L141](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/layers/tortoise/diffusion_decoder.py#L141), and the CLVP text-audio reranker at [L20](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/layers/tortoise/clvp.py#L20).

## The Vocoder Shelf and Audio Glue

Spectrogram models need a vocoder, and the shelf in `TTS/vocoder/models/` is organized as one framework plus interchangeable generators. The framework is [GAN, L21](https://github.com/coqui-ai/TTS/blob/dev/TTS/vocoder/models/gan.py#L21), a [BaseVocoder, L8](https://github.com/coqui-ai/TTS/blob/dev/TTS/vocoder/models/base_vocoder.py#L8) subclass whose [forward, L47](https://github.com/coqui-ai/TTS/blob/dev/TTS/vocoder/models/gan.py#L47) returns scores from every discriminator and whose [inference, L58](https://github.com/coqui-ai/TTS/blob/dev/TTS/vocoder/models/gan.py#L58) runs just the generator — the same class serves HiFi-GAN, MelGAN, ParallelWaveGAN, and UnivNet by swapping components. The default generator is [HifiganGenerator, L162](https://github.com/coqui-ai/TTS/blob/dev/TTS/vocoder/models/hifigan_generator.py#L162), a stack of ResBlock upsamples that is now the industry's favorite mel-to-wav module; [Wavernn, L193](https://github.com/coqui-ai/TTS/blob/dev/TTS/vocoder/models/wavernn.py#L193) is the older RNN alternative. This generator-versus-discriminator design is the same intellectual territory as Meta's audio generative work in [Audiocraft](/audiocraft/), and the separation-of-concerns pays off when you want to re-voice or remix audio the way [Demucs](/demucs/) does for stems.

The glue around the models is unglamorous and essential. On the text side, [TTSTokenizer, L10](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/utils/text/tokenizer.py#L10) composes cleaners, punctuation, and a phonemizer; [text_to_ids, L87](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/utils/text/tokenizer.py#L87) is the one line that turns a sentence into model input, while the espeak-ng wrapper [ESpeak, L83](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/utils/text/phonemizers/espeak_wrapper.py#L83) does grapheme-to-phoneme conversion with language wrappers for Japanese, Korean, Chinese, and more alongside it. XTTS's cloner tokenizer instead uses byte-pair subwords — the same family of techniques as [sentencepiece](/sentencepiece/) — because GPT-style models want subword vocabularies, not phonemes. Speaker identity is handled by [EmbeddingManager, L109](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/utils/managers.py#L109), the base that maps names to embedding vectors, which `SpeakerManager` in `TTS/tts/utils/speakers.py` specializes. On the audio side, [AudioProcessor, L32](https://github.com/coqui-ai/TTS/blob/dev/TTS/utils/audio/processor.py#L32) owns mel conversions and normalization, the `synthesis()` function at [L116](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/utils/synthesis.py#L116) is the per-sentence inference pass the Synthesizer loops over (with a voice-transfer variant at [L255](https://github.com/coqui-ai/TTS/blob/dev/TTS/tts/utils/synthesis.py#L255)), and [save_wav, L430](https://github.com/coqui-ai/TTS/blob/dev/TTS/utils/audio/numpy_transforms.py#L430) writes the final file — the Synthesizer's own [save_wav, L238](https://github.com/coqui-ai/TTS/blob/dev/TTS/utils/synthesizer.py#L238) delegates to it, optionally piping bytes to stdout for shell use.

## Honest Limits

The `dev` branch we toured is a snapshot, not a moving target: its most recent commit at tour time dates to February 2024, and the README still leads with XTTSv2 announcements rather than any deprecation notice, so read the repository as a stable, self-contained reference implementation. Two things are explicitly retired in the code itself: the Coqui Studio cloud models — [L235](https://github.com/coqui-ai/TTS/blob/dev/TTS/api.py#L235) raises a ValueError naming them as discontinued — and the `gpu=` constructor flag, which warns at [L70](https://github.com/coqui-ai/TTS/blob/dev/TTS/api.py#L70) in favor of `tts.to(device)`. The training loop depends on the separate `trainer` package, so reproducibility of a fine-tune means pinning two repositories, not one. Inference is pure PyTorch: there is no built-in export to ONNX or any mobile runtime, which is exactly the gap lightweight runtimes like [Piper](/piper/) fill for embedded use. Finally, phonemization shelling out to espeak-ng means some models need a system binary installed — the pure-Python part of the install is not always the whole install.
