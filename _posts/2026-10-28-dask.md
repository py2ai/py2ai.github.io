Dask has become the default answer to a very common moment in a data scientist's life: the moment your pandas DataFrame no longer fits in RAM, or your numpy array of features outgrows a single machine. Instead of asking you to rewrite your code, Dask partitions the data, records every operation you perform as a node in a task graph, and executes that graph — on threads, on processes, or on a cluster — only when you finally ask for a result. It is lazy evaluation wearing a pandas mask, and it has quietly become the substrate under everything from ETL scripts to distributed model training.

What makes the codebase fascinating is that the entire system rests on a handful of small, readable ideas. A task graph is literally a dictionary mapping keys to runnable objects. A collection is a thin wrapper that knows how to produce such a dictionary. An optimizer rewrites expressions before they become graphs. A scheduler loop walks the resulting dictionary, executing each node when its inputs are ready. Everything else — DataFrame, Array, delayed, futures — is composition on top of those four ideas. In this tour we clone the repository at its default branch and follow those ideas through the actual files, line by line, so the next time `compute()` takes ninety seconds you will know exactly what it is doing in there.

The other thing worth knowing up front is that Dask has been migrating its DataFrame internals to an expression system called dask-expr, and on current main that migration is essentially complete: the classes you import as `dask.dataframe.DataFrame` now live in `dask/dataframe/dask_expr/_collection.py`, and a general expression base lives in `dask/_expr.py`. Older blog posts that point you at `dask/dataframe/frame.py` are describing a file that no longer exists. Our diagrams below reflect the tree as it actually is today.

<p><em>Overview of Dask as actually laid out on main: collections share the mixin protocol in base.py, optimize through the expression layer, materialize into a HighLevelGraph of Task and DataNode objects, and run on schedulers that all drive one async loop in local.py.</em></p>

Reading the overview from left to right:

- [Task, L636](https://github.com/dask/dask/blob/main/dask/_task_spec.py#L636) is the runnable atom: a key, a function, and arguments that may reference other keys.
- [DataNode, L575](https://github.com/dask/dask/blob/main/dask/_task_spec.py#L575) holds a literal value directly in the graph, the other half of every graph dictionary.
- [HighLevelGraph, L364](https://github.com/dask/dask/blob/main/dask/highlevelgraph.py#L364) layers per-collection subgraphs into one mapping so two DataFrames can share structure without copying keys.
- [DaskMethodsMixin, L269](https://github.com/dask/dask/blob/main/dask/base.py#L269) is the tiny base class that gives every collection `compute`, `persist`, and `visualize`.
- [compute, L685](https://github.com/dask/dask/blob/main/dask/base.py#L685) is the front door: it accepts many collections, optimizes their graphs, and dispatches to one scheduler.
- [optimize, L903](https://github.com/dask/dask/blob/main/dask/_expr.py#L903) is the expression-system optimizer that fuses operations before any graph is built.
- [get, L62](https://github.com/dask/dask/blob/main/dask/threaded.py#L62) is the default local scheduler, submitting tasks to a thread pool.
- [get_async, L382](https://github.com/dask/dask/blob/main/dask/local.py#L382) is the state-machine loop that every local scheduler, threaded or not, actually drives.
- [DataFrame, L2689](https://github.com/dask/dask/blob/main/dask/dataframe/dask_expr/_collection.py#L2689) and [Array, L1300](https://github.com/dask/dask/blob/main/dask/array/core.py#L1300) are the two flagship collections — partitioned pandas and chunked numpy respectively.

## The Detail View: Follow One read_csv Call

<div style="overflow-x:auto;"><img src="/assets/img/diagrams/dask/dask-dask-architecture.svg" alt="Dask detail architecture: graph and keys, collection protocol, optimizer, local schedulers, DataFrame expression internals, array internals, and delayed" style="min-width:900px;"></div>

<p><em>The detail view: how a lazy call like dd.read_csv travels through the expression tree, becomes a HighLevelGraph of Task nodes, and lands in the get_async scheduling loop.</em></p>

Start with `dd.read_csv("trips.csv")`. Nothing is read yet. The public name is created dynamically in [csv.py, L748](https://github.com/dask/dask/blob/main/dask/dataframe/io/csv.py#L748), where `make_reader` wraps pandas' own reader so custom backends can register their own variants. Calling it samples the file, infers dtypes, computes a sensible byte-chunk size with [auto_blocksize, L394](https://github.com/dask/dask/blob/main/dask/dataframe/io/csv.py#L394), and returns a DataFrame collection whose value is an expression tree, not data. When you later call `.groupby().sum()`, the tree simply grows; when you call `compute()`, the optimizer walks the tree, fuses adjacent expressions into [Fused, L3787](https://github.com/dask/dask/blob/main/dask/dataframe/dask_expr/_expr.py#L3787) nodes, lowers everything to a HighLevelGraph, culls every key that is not on the path to your requested outputs, and hands the remaining dictionary to a scheduler. That is the entire life of a query — and the same story, with different expression classes, applies to arrays built from [from_array, L3468](https://github.com/dask/dask/blob/main/dask/array/core.py#L3468).

## The Task Is the Unit of Work

Open `dask/_task_spec.py` and you find the vocabulary of the whole system. Every node in a graph is a `GraphNode` subclass ([GraphNode, L378](https://github.com/dask/dask/blob/main/dask/_task_spec.py#L378)). The runnable kind is [Task, L636](https://github.com/dask/dask/blob/main/dask/_task_spec.py#L636), which bundles a key, a callable, and arguments; when arguments need values produced by other tasks they are wrapped in [TaskRef, L333](https://github.com/dask/dask/blob/main/dask/_task_spec.py#L333), and calling the Task with a dictionary of resolved values executes it — the docstring shows a two-input add resolving to 3. The literal kind is [DataNode, L575](https://github.com/dask/dask/blob/main/dask/_task_spec.py#L575), and an [Alias, L512](https://github.com/dask/dask/blob/main/dask/_task_spec.py#L512) is a graph-level rename that costs nothing to evaluate.

Two helpers turn this vocabulary into a schedulable structure. [get_dependencies, L213](https://github.com/dask/dask/blob/main/dask/core.py#L213) walks a task's arguments and returns the set of keys it immediately needs — the scheduler calls this constantly while deciding what is runnable. And when a fully materialized dictionary is available, [execute_graph, L1064](https://github.com/dask/dask/blob/main/dask/_task_spec.py#L1064) evaluates it directly, which is exactly what the expression layer does for small fused subgraphs: rather than submitting every micro-task to the pool, related tasks are bundled and run inline.

## From Expressions to Schedulable Graphs

The modern optimization story lives in two places. The generic half is `dask/_expr.py`, whose [Expr, L50](https://github.com/dask/dask/blob/main/dask/_expr.py#L50) base class defines how an operation describes itself and how its graph contribution is produced lazily; [SingletonExpr, L861](https://github.com/dask/dask/blob/main/dask/_expr.py#L861) deduplicates structurally identical nodes, and [optimize, L903](https://github.com/dask/dask/blob/main/dask/_expr.py#L903) is the recursive rewrite entry that `compute()` invokes. When rewriting finishes, the tree bottoms out in an [HLGExpr, L974](https://github.com/dask/dask/blob/main/dask/_expr.py#L974) that wraps a materialized HighLevelGraph, and a terminal [FinalizeCompute, L1315](https://github.com/dask/dask/blob/main/dask/_expr.py#L1315) node marks where results are gathered.

The DataFrame-specific half lives under `dask/dataframe/dask_expr/`. Its [Expr, L70](https://github.com/dask/dask/blob/main/dask/dataframe/dask_expr/_expr.py#L70) specializes the generic base for pandas metadata, divisions, and column tracking; [Elemwise, L1332](https://github.com/dask/dask/blob/main/dask/dataframe/dask_expr/_expr.py#L1332) is the workhorse that pushes elementwise pandas operations into partitions so several can fuse into one pass over each partition. For the array side, the classic tool is [blockwise, L227](https://github.com/dask/dask/blob/main/dask/blockwise.py#L227), which builds a layer of tasks across the cartesian product of chunk indices, and [optimize_blockwise, L1077](https://github.com/dask/dask/blob/main/dask/blockwise.py#L1077), which fuses adjacent such layers so a chain like `x.T + y` becomes one fat task per chunk instead of four thin ones; [fuse_roots, L1514](https://github.com/dask/dask/blob/main/dask/blockwise.py#L1514) then stitches the fused core to the graph's input layers. This is why a chain of twenty array operations costs the scheduler almost nothing: after fusion it is a handful of tasks.

## One Engine, Three Schedulers

Every local scheduler in the repo is a thin costume over the same engine. [get_async, L382](https://github.com/dask/dask/blob/main/dask/local.py#L382) maintains a small state machine: keys ready to run, keys currently running, keys waiting on dependencies, and results. It ranks ready keys with the heuristic from [order, L81](https://github.com/dask/dask/blob/main/dask/order.py#L81) — imported at [local.py, L123](https://github.com/dask/dask/blob/main/dask/local.py#L123) — which scores each key by how much downstream work it unblocks, so the graph tends to run critical-path-first. Actual execution goes through [execute_task, L246](https://github.com/dask/dask/blob/main/dask/local.py#L246), and completion bookkeeping through [finish_task, L290](https://github.com/dask/dask/blob/main/dask/local.py#L290), which records the result and decrements the pending-dependency counts of everything that was waiting.

The threaded scheduler in [get, L62](https://github.com/dask/dask/blob/main/dask/threaded.py#L62) simply owns a [ContextAwareThreadPoolExecutor, L39](https://github.com/dask/dask/blob/main/dask/threaded.py#L39), reusing a global pool when run from the main thread, and hands `pool.submit` to `get_async`. The process-based scheduler at [get, L147](https://github.com/dask/dask/blob/main/dask/multiprocessing.py#L147) does the same with a process pool, adding exception packing so tracebacks survive the pickle round-trip. And [get_sync, L587](https://github.com/dask/dask/blob/main/dask/local.py#L587) — the `scheduler="synchronous"` option — drives the identical loop with no pool at all, which makes it the best debugging tool in the repo: every task runs on your main thread, in priority order, with real tracebacks.

## From Install to Your First Model

The complete distribution installs with `pip install "dask[complete]"`, which pulls in the DataFrame, Array, Bag, and delayed APIs plus their dependencies. The fastest way to feel the machinery is delayed, which turns ordinary Python calls into graph nodes:

```python
import dask
from dask import delayed

@delayed
def load(path):
    return open(path).read().split()

@delayed
def count(tokens):
    return len(tokens)

files = ["a.txt", "b.txt", "c.txt"]
total = delayed(sum)([count(load(f)) for f in files])
total.visualize("counts.svg")  # the graph, before any I/O happens
print(total.compute())         # only now do files open
```

For tabular work, the collection API mirrors pandas so closely that the port usually amounts to renaming the import and letting Dask pick the partition count — our earlier tour of [pandas](/pandas/) covers the single-node semantics being parallelized here:

```python
import dask.dataframe as dd

df = dd.read_csv("trips-*.csv")            # lazy: schema sampled, data untouched
daily = df.groupby("day")["fare"].mean()   # the expression tree grows
daily = daily.persist()                    # materialize once, reuse many times
print(daily.compute())
```

Under the hood `read_csv` builds an IO expression, `persist` runs the optimizer and pins each partition in memory, and `compute` executes whatever is left. Arrays work the same way for tensor-shaped data — chunked numpy with the same three method names; if you want the single-machine numpy semantics that each chunk preserves, see our [numpy](/numpy/) tour. A minimal end-to-end model is now just sklearn on the computed result: fit on `daily.compute()`, or use `dask-ml` for out-of-core fitting.

## Honest Limits

The local schedulers are single-machine by design. `dask/threaded.py` and `dask/multiprocessing.py` are a few hundred lines each because the distributed scheduler lives in a separate repository and does the real cluster work — everything here assumes one box, one shared memory space, and a `multiprocessing.Pool`-style executor at most.

Threads only help when the GIL is released. Dask's default pool is a thread pool precisely because numpy and pandas spend their time in C code, but pure-Python tasks will serialize embarrassingly; if your tasks are Python-heavy you must switch to processes or distributed, and then pay for pickling every input and output.

The expression layer is still settling. The migration to dask-expr rewrote the DataFrame internals almost wholesale, and rewrite rules are added release by release — code that depended on graph internals, or on optimizations not yet ported, can behave differently across versions. Always pin your version in production.

Finally, Dask is not the answer to every scale problem. For datasets that fit in a few gigabytes, modern single-node engines often beat it on both speed and simplicity: our [polars](/polars/) and [duckdb](/duckdb/) tours cover query engines that push vectorized execution much harder than a task graph can. Dask's edge is generality — arbitrary Python, arrays, custom computations, and a clean path from your laptop to a cluster without changing the code.
