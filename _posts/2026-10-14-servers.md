Every protocol gets one repository that is less a product than a manners guide. For the Model Context Protocol, it is [modelcontextprotocol/servers](https://github.com/modelcontextprotocol/servers): seven small servers that thousands of client implementations were implicitly trained on. A filesystem server whose security layer has eleven hundred lines of adversarial path tests. A fetch server that checks robots.txt before a model does something embarrassing. A memory server that persists a knowledge graph to JSON with file locking and atomic saves, because two agents sharing one brain is a concurrency problem. The sequential-thinking server, whose single tool changed how models plan. And the everything server, a deliberate demonstration animal that exercises sampling, elicitation, progress notifications, resource templates, and four transports so that implementers never have to guess what "the protocol" includes. The code is TypeScript and Python, mixed freely, and every package carries a protocol test suite thicker than the server itself. Reading this repository is not reading seven tools — it is reading the style guide the MCP ecosystem absorbed.

The architecture is a flat collection with shared conventions rather than shared code. Each directory under src/ is a self-contained server: a manifest, a transport entry point, tool handlers, and a test suite that drives the real protocol rather than mocking it. The TypeScript servers (filesystem, memory, sequentialthinking, everything) sit beside the Python ones (fetch, git, time), which communicates something deliberate — an MCP server is a contract, not a framework choice. The filesystem package is the deepest, splitting tool registration from a typed operations library from a validation layer. The everything package is the widest, one file per protocol capability with transports for stdio, SSE, streamable HTTP, and an in-memory event store for resumability. The repository itself dogfoods the protocol — its .mcp.json configures the project's own development agents with the servers it ships — and points beyond itself in ADDITIONAL.md, the curated community index. As always in this series, what follows is an educational tour of published source code.

Reading the overview from left to right:

- [The filesystem server](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/server.ts) registers every file operation as a tool with typed schemas.
- [The path validation layer](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/path-validation.ts) keeps operations inside allowed roots, symlinks considered.
- [The fetch server](https://github.com/modelcontextprotocol/servers/blob/main/src/fetch/src/mcp_server_fetch/server.py) converts web pages to markdown with robots.txt respect and domain blocking.
- [The git server](https://github.com/modelcontextprotocol/servers/blob/main/src/git/src/mcp_server_git/server.py) wraps repository operations behind an explicit safety posture.
- [The memory server](https://github.com/modelcontextprotocol/servers/blob/main/src/memory/index.ts) persists a knowledge graph of entities and relations to a JSON file.
- [The thinking server](https://github.com/modelcontextprotocol/servers/blob/main/src/sequentialthinking/index.ts) gives models a revisable, branchable scratchpad.
- [The everything server](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/index.ts) demonstrates every protocol feature end to end.
- [The community index](https://github.com/modelcontextprotocol/servers/blob/main/ADDITIONAL.md) catalogs the ecosystem that grew around these seven.

## Why You Need This

The first reason is the security engineering, because the filesystem server is the best publicly readable example of "letting an AI touch your disk, carefully." [The server](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/server.ts) registers read, write, move, search, and edit tools with Zod schemas, then funnels every path argument through [the validation layer](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/path-validation.ts), which resolves symlinks and enforces root containment before anything touches disk. [The path utilities](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/path-utils.ts) handle the cross-platform noise — home expansion, normalization, Windows quirks — and [the roots module](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/roots-utils.ts) merges the protocol's root declarations with configured directories, so a client can reshape the writable surface at runtime. What makes this package required reading is the evidence: [eleven hundred lines of path-validation tests](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/__tests__/path-validation.test.ts) attack the boundary with traversal tricks and platform-specific cases, [another eleven hundred cover the tool handlers](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/__tests__/server-tools.test.ts), and seven hundred more pin how roots change behavior. This is what "safe by default" looks like when someone actually pays for it.

The second reason is the behavioral servers, because memory and sequential thinking changed what models do more than any single tool since. [The memory server](https://github.com/modelcontextprotocol/servers/blob/main/src/memory/index.ts) implements a knowledge graph — entities with observations, relations with directions, searched by exact and fuzzy match — persisted to a JSON file the agent owns. The interesting code is not the graph but the persistence discipline: [file-lock tests](https://github.com/modelcontextprotocol/servers/blob/main/src/memory/__tests__/file-lock.test.ts) prove concurrent writers cannot corrupt the store, and [atomic-save tests](https://github.com/modelcontextprotocol/servers/blob/main/src/memory/__tests__/atomic-save.test.ts) cover the write-temp-then-rename path that survives a crash mid-save. [The thinking server](https://github.com/modelcontextprotocol/servers/blob/main/src/sequentialthinking/index.ts) is the opposite of subtle — one tool, one scratchpad — but [its library](https://github.com/modelcontextprotocol/servers/blob/main/src/sequentialthinking/lib.ts) tracks revisions and branches, letting a model mark a thought as revised or pivot to an alternative chain, and [the behavior tests](https://github.com/modelcontextprotocol/servers/blob/main/src/sequentialthinking/__tests__/thinking.test.ts) pin those semantics. Both servers are under eleven hundred lines; both were copied more times than any framework in the ecosystem.

The third reason is the everything server, because it is the executable answer to "what does MCP actually support." [Its assembly](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/index.ts) wires [a server factory](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/server/index.ts) to one tool per capability: [sampling triggers](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/tools/trigger-sampling-request.ts) show a server asking the client's model for a completion, [elicitation triggers](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/tools/trigger-elicitation-request.ts) show schema-validated input requests, [a long-running operation](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/tools/trigger-long-running-operation.ts) streams progress notifications, and the resources modules cover [URI-templated resources](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/resources/templates.ts) and [update subscriptions](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/resources/subscriptions.ts). On the transport side, [stdio](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/transports/stdio.ts) serves local clients while [streamable HTTP](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/transports/streamableHttp.ts) adds sessions with resumability through [an in-memory event store](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/transports/in-memory-event-store.ts). The Python members complete the picture: [the fetch server](https://github.com/modelcontextprotocol/servers/blob/main/src/fetch/src/mcp_server_fetch/server.py) with its domain blocking, [the git server](https://github.com/modelcontextprotocol/servers/blob/main/src/git/src/mcp_server_git/server.py) keeping read operations explicit, and [the time server](https://github.com/modelcontextprotocol/servers/blob/main/src/time/src/mcp_server_time/server.py) as the minimal complete example teachers keep reaching for.

The detail view makes the test-first culture visible. In the filesystem group, three test suites point at three production modules, and the arrows from validation into the library show the boundary being enforced inside the operations, not around them. The Python servers mirror the pattern — protocol test suites nearly as long as their servers — which is how a polyglot collection stays consistent. The memory group's three suites graph onto one index file, a ratio that tells you where the risk lives. And the everything group is the only place where production and demonstration share a diagram: its tools exist to be triggered, its transports to be replayed, its event store to prove that resumability is a protocol property rather than a vendor feature.

## From Install to a Working Client Config

These servers are built to be launched by an MCP client, so the setup is a config file rather than an app. For the filesystem server, add an entry to your client's configuration — Claude Desktop's claude_desktop_config.json is the canonical example — running `npx @modelcontextprotocol/server-filesystem` with one or more allowed directories as arguments; the tools appear in your client and the boundary is those directories. The Python servers install through uv or pip and run as modules: `uvx mcp-server-fetch` for web fetching, `mcp-server-git --repository path` for a repository, `mcp-server-time` for time tools, each over stdio unless you pass transport flags. The everything server runs the same way (`npx @modelcontextprotocol/server-everything`) and exists specifically to be poked at — trigger its sampling or elicitation tools from any client and watch the protocol behave. For development on this repository itself, each package carries its own test command, and the protocol tests are the fastest way to understand a server: run them with the harness output visible and you are watching MCP conversations, annotated.

Honest limits: this is the reference collection, not a product line — several servers are explicitly minimal, maintained as examples first, and the README says as much. The fetch server's dependence on third-party page structures means web handling needs supervision, and its robots and domain-blocking defaults are conservative by design. The memory server's JSON persistence is honest about its ceiling: it is a single-file store with locking, not a database, and multi-host deployments outgrow it. The licensing story is mid-transition — the project is moving from MIT to Apache-2.0 with a documented consent process, so check the LICENSE file before redistribution. And the everything server is a demonstration animal: run it for its teaching value, not anywhere that matters.
