If you have trained a model on a public corpus in the last five years, the odds are very high that the data reached you through huggingface/datasets. The library is the de facto data layer of the open-source model ecosystem: one call to load_dataset pulls a named dataset from the Hub, converts it to Arrow, caches it under your home directory, and returns an object you can index, filter, shuffle, and hand straight to a training loop. The model-loading side of that ecosystem is covered in our [Transformers](/transformers/) tour, and the tokenization layer in the [Tokenizers](/tokenizers/) walkthrough — datasets is the quieter component that feeds both of them every single day.

The source deserves a careful read because the library makes a series of pragmatic engineering decisions that show up directly in your own projects: content-addressed caches made of hash-named folders, memory-mapped Arrow files that allow zero-copy reads from many worker processes, and fingerprinted transformations so the output of an expensive map survives across sessions. Once you understand how those pieces connect, mysterious disk usage and re-downloads stop being mysterious — they become predictable consequences of a design you can point at line by line. That is exactly what this post is for.

Our tour follows a stage-wise flow through the repository at its current main branch: public entry points, then the discovery stage that turns glob patterns into concrete files, then the builder stage that downloads sources and generates examples, then the Arrow layer that writes and reads shards, and finally the in-memory objects you actually hold in a notebook. Read together, they describe one continuous arrow data flow from a URL on the Hub to a typed table inside your Python process. Every symbol link below was checked against the checked-out HEAD before publishing, so the line anchors are real.

## What the Library Actually Ships

The first surprise in `src/datasets` is how flat the core is. There is no tall stack of abstractions: `arrow_dataset.py` is a single very large module holding the eager Dataset class and its transformations, `load.py` contains the user-facing resolution logic, and `builder.py` defines the DatasetBuilder base class that every format-specific builder extends. Network behavior is quarantined in the `download/` subpackage, which separates DownloadManager, StreamingDownloadManager, and DownloadConfig from everything else — a clean seam that keeps the rest of the code testable without touching the network.

Around that core sit three supporting rings. The `packaged_modules/` tree contains ready-made builders for parquet, CSV, JSON, imagefolder, audiofolder, and dozens of other formats; the Parquet builder at [Parquet, L93](https://github.com/huggingface/datasets/blob/main/src/datasets/packaged_modules/parquet/parquet.py#L93) is the one most Hub repositories hit today. Metadata lives in `info.py` and `splits.py`, while the typed column schema — including audio, image, and video columns — is defined in [Features, L1923](https://github.com/huggingface/datasets/blob/main/src/datasets/features/features.py#L1923). Runtime constants such as the cache root live in `config.py`, starting with [HF_DATASETS_CACHE, L161](https://github.com/huggingface/datasets/blob/main/src/datasets/config.py#L161).

## The Overview, Stage by Stage

<div style="overflow-x:auto;"><img src="https://pyshine.com/assets/img/diagrams/datasets/huggingface-datasets-overview-architecture.svg" alt="Hugging Face Datasets architecture overview" style="max-width:100%;"></div>

<p><em>The overview diagram traces the arrow data flow from load_dataset through builder caching to the Dataset objects returned to the caller.</em></p>

Reading the overview from left to right:

- The public entry point is [load_dataset, L1446](https://github.com/huggingface/datasets/blob/main/src/datasets/load.py#L1446), which normalizes arguments and decides between an eager DatasetDict, a single Dataset, or a lazy streaming variant.
- It delegates resolution to [load_dataset_builder, L1187](https://github.com/huggingface/datasets/blob/main/src/datasets/load.py#L1187), which imports the right builder module and instantiates it with your configuration.
- When you pass local files, the discovery stage calls into [DataFilesDict, L650](https://github.com/huggingface/datasets/blob/main/src/datasets/data_files.py#L650), which resolves glob patterns and Hub URLs into a concrete, sorted list of source files.
- The build stage is anchored by [DatasetBuilder, L214](https://github.com/huggingface/datasets/blob/main/src/datasets/builder.py#L214), whose [download_and_prepare, L702](https://github.com/huggingface/datasets/blob/main/src/datasets/builder.py#L702) method orchestrates the entire caching run and skips work when the cache is already valid.
- Fetching itself is the job of [DownloadManager, L71](https://github.com/huggingface/datasets/blob/main/src/datasets/download/download_manager.py#L71), which hands the author-defined split hook a small API for requesting URLs and archives.
- Generated examples are serialized by [ArrowWriter, L514](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_writer.py#L514), which infers a schema from the first examples and appends rows into Arrow shard files on disk.
- On the way back out, [ArrowReader, L285](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_reader.py#L285) rebuilds tables from those shards; nothing re-runs the generators when the cache is warm.
- Finally [Dataset, L709](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_dataset.py#L709) wraps the materialized table, and [DatasetDict, L53](https://github.com/huggingface/datasets/blob/main/src/datasets/dataset_dict.py#L53) maps split names such as train and test onto those objects.

The important property of this flow is that it is resumable at every stage. The download cache, the generated Arrow cache, and the fingerprint cache are three separate layers, each with its own invalidation rule, so a failed run usually costs you only the unfinished stage rather than the whole preparation.

## From Install to Your First Model

Installation is deliberately boring: `pip install datasets` brings in PyArrow, huggingface-hub, and a handful of small dependencies. Your first real interaction looks like this:

```python
from datasets import load_dataset

ds = load_dataset("ag_news")
print(ds["train"][0]["text"][:120])
```

One line hides the whole stage-wise flow from the overview. The library resolves ag_news on the Hub, downloads and unpacks its parquet shards through the download layer, writes an Arrow copy into your cache, and returns a DatasetDict of eager splits. Everything after that point reads from local disk: indexing a row is a memory-mapped lookup, not a network call, which is why you can share one cache across many experiments without ever re-downloading.

Transformations are where the design earns its keep. The map method at [map, L3205](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_dataset.py#L3205) applies a function across rows and caches the result under a fingerprint derived from the function's bytecode and closure; its sibling [filter, L4134](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_dataset.py#L4134) is a predicate built on the same machinery, and [shuffle, L4827](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_dataset.py#L4827) creates deterministic permutations that survive restarts. A typical preprocessing chain looks like this:

```python
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("distilbert-base-uncased")

ds = ds.map(lambda x: tok(x["text"]), batched=True)
ds = ds.with_format("torch")
```

Calling [with_format, L2997](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_dataset.py#L2997) changes how rows are materialized — torch tensors, NumPy arrays, pandas frames, or JAX arrays — without copying the underlying Arrow table. That final tensor view is what you feed to a training loop built on [PyTorch](/pytorch/); the Arrow columns stay on disk and each batch is assembled lazily. If your per-row work is the expensive part, the fingerprint cache means the second run of the same map is nearly free, even in a fresh process.

Two more everyday methods round out the eager surface. [train_test_split, L4967](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_dataset.py#L4967) carves deterministic holdout sets out of a single table, and [select, L4359](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_dataset.py#L4359) builds a view over an explicit index list — both return new Dataset objects that share the parent's Arrow memory until a transformation forces materialization. When your data starts as plain Python, [from_dict, L983](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_dataset.py#L983) converts a dictionary of lists into a full Dataset, inferring Features along the way. And once a cleaned version of a corpus is worth sharing, [push_to_hub, L6070](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_dataset.py#L6070) uploads the Arrow shards and a generated README card back to the Hub, closing the loop between consumers and producers of data.

## The Detail Diagram: One Call, Six Modules

<div style="overflow-x:auto;"><img src="https://pyshine.com/assets/img/diagrams/datasets/huggingface-datasets-architecture.svg" alt="Hugging Face Datasets detail architecture" style="max-width:100%;"></div>

<p><em>The detail diagram expands the stage-wise flow into individual methods and shows how the download, build, Arrow, and in-memory layers interlock.</em></p>

The detail view rewards a slow walk. Inside download_and_prepare, the builder first asks the author-defined hook [_split_generators, L1197](https://github.com/huggingface/datasets/blob/main/src/datasets/builder.py#L1197) for a plan; each returned [SplitGenerator, L624](https://github.com/huggingface/datasets/blob/main/src/datasets/splits.py#L624) binds a split name to a shard key, and their byte counts end up registered in [SplitDict, L530](https://github.com/huggingface/datasets/blob/main/src/datasets/splits.py#L530) inside the DatasetInfo record at [DatasetInfo, L92](https://github.com/huggingface/datasets/blob/main/src/datasets/info.py#L92). The download requests made inside that hook flow through [cached_path, L129](https://github.com/huggingface/datasets/blob/main/src/datasets/utils/file_utils.py#L129), which understands local paths, HTTP URLs, and Hub references, all tunable per call via [DownloadConfig, L10](https://github.com/huggingface/datasets/blob/main/src/datasets/download/download_config.py#L10).

The right half of the diagram shows the exit paths. The cached shards become objects through [as_dataset, L991](https://github.com/huggingface/datasets/blob/main/src/datasets/builder.py#L991), which routes [read_files, L254](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_reader.py#L254) results into Dataset instances; a completed folder can be re-opened later with load_from_disk after save_to_disk exports it, using the pair [save_to_disk, L1781](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_dataset.py#L1781) and [load_from_disk, L1704](https://github.com/huggingface/datasets/blob/main/src/datasets/load.py#L1704). The lazy alternative bypasses the Arrow cache entirely: in streaming mode, load_dataset returns [IterableDataset, L2690](https://github.com/huggingface/datasets/blob/main/src/datasets/iterable_dataset.py#L2690), whose shard iteration is backed by the lazy [StreamingDownloadManager, L47](https://github.com/huggingface/datasets/blob/main/src/datasets/download/streaming_download_manager.py#L47) and installed by [extend_module_for_streaming, L42](https://github.com/huggingface/datasets/blob/main/src/datasets/streaming.py#L42). Both modes share the same Features schema, so a dataset that streams can later be materialized with the same columns and types.

The writer side of the diagram deserves its own note. [write_table, L804](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_writer.py#L804) appends each incoming batch to the current shard and rolls over at a configurable size, while [finalize, L829](https://github.com/huggingface/datasets/blob/main/src/datasets/arrow_writer.py#L829) closes the file, writes the footer, and reports the byte and row totals that metadata later records. On the ingest side, [download_and_extract, L310](https://github.com/huggingface/datasets/blob/main/src/datasets/download/download_manager.py#L310) chains fetching and unpacking for archives, and the split of responsibilities is strict: the builder decides what to generate, the manager decides where bytes come from, and the writer decides how they land on disk.

## Honest Limits

The caching design has sharp edges worth naming. The Arrow cache is append-oriented: changing a builder configuration creates a new config id and therefore a new cache directory, and nothing garbage-collects the old one for you. Long experiment sessions can quietly accumulate dozens of gigabytes across `~/.cache/huggingface`, so you should prune deliberately rather than discover the growth at the worst time. Fingerprint invalidation for map is conservative — it hashes the function's bytecode, not its semantics — so editing a comment can invalidate a cache while editing a global constant may not, and there is no way to express fine-grained dependencies.

The eager Dataset also assumes its table fits comfortably on disk, and mostly in memory when you transform aggressively. map with num_proc multiplies memory pressure by worker count, and shuffling very wide tables can force the sort-based fallback that materializes indices. Streaming mode removes the disk cost but gives up random access, shuffling becomes a buffered approximation, and you cannot know the dataset length without an extra Hub query. Finally, datasets is a table cache with opinions, not a query engine: there is no SQL layer, no joins, and no server; complex relational work belongs in your own tooling, with datasets as the typed import and export layer. None of these are bugs — they are the documented cost of a design that puts resume-ability and speed ahead of everything else.

What you take away from the source is a set of transferable patterns: hash-addressed caches you can copy into any batch job, a builder contract that separates format authors from caching machinery, and an Arrow-first storage discipline that scales from a laptop to a training cluster. When you next reach for load_dataset, you will know precisely which lines run, in which order, and why your disk looks the way it does.
