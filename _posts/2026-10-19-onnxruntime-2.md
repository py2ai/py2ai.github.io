Our first walk of [microsoft/onnxruntime](/onnxruntime/) stayed at the architectural level: the versioned C API, the fusion transformers, MLAS, the CUDA provider, and the training stack. That post ends where every session ends up on a hot path — a call to `Run()` with a dictionary of feeds — and leaves the most performance-critical half of the codebase unexplored: what actually happens between that call and the last kernel's write. This tour follows exactly that half. It is a story with three distinct layers. At the top, [InferenceSession::RunImpl](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/session/inference_session.cc#L3713) validates options and hands the plan to an executor. In the middle, [ExecuteThePlan](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/sequential_executor.cc#L686) walks the graph across a small set of device streams, checking barriers before each node fires. At the bottom, an ExecutionFrame and a best-fit-coalescing arena have already pre-computed — at session initialization time — where every byte of every intermediate tensor will live, so that a steady-state inference run performs almost no allocator decision-making at all. As always in this series, this is an educational read of published MIT-licensed source on the main branch; the first post at /onnxruntime/ covers the API surface and provider layer that this machinery serves.

The headline is that ONNX Runtime treats allocation as a compile-time problem, not a runtime one. Two planners run during Initialize, not during inference: one assigns nodes and weights to devices, the other traces every buffer's lifetime and folds the resulting sizes into reusable memory patterns. By the time Run() is called, the expensive questions have yes-or-no answers cached in the session state, and the per-run work reduces to bookkeeping — which is why the code can afford a comparatively elegant stream walk in the middle.

Reading the overview from left to right:

- [inference_session.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/session/inference_session.cc) is the public face: [Load](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/session/inference_session.cc#L1287) for file paths, [RunImpl](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/session/inference_session.cc#L3713) for the hot path, and [RunAsync](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/session/inference_session.cc#L4141) at 4141 for the callback variant.
- [sequential_executor.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/sequential_executor.cc) holds [ExecuteThePlan](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/sequential_executor.cc#L686) and [ExecuteKernel](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/sequential_executor.cc#L527) — the modern stream-based execution loop that replaced the old class-based executors.
- [stream_execution_context.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/stream_execution_context.cc) defines the per-run context whose constructor starts at [line 12](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/stream_execution_context.cc#L12), with [DecCountDownBarrier](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/stream_execution_context.cc#L73) enforcing launch order.
- [device_stream_collection.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/device_stream_collection.cc) builds one stream per EP stream id: [SetDeviceStream](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/device_stream_collection.cc#L154) fills the set, [GetStreamForDevice](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/device_stream_collection.cc#L178) looks it back up.
- [cuda_stream_handle.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/providers/cuda/cuda_stream_handle.cc) is the concrete NVIDIA handle: [EnqueDeferredCPUBuffer](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/providers/cuda/cuda_stream_handle.cc#L125) and [CleanUpOnRunEnd](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/providers/cuda/cuda_stream_handle.cc#L163) manage host-side work on device time.
- [allocation_planner.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/allocation_planner.cc) at 2600+ lines contains [PlannerImpl::CreatePlan](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/allocation_planner.cc#L2393) and the [DeviceBasedPartitioner](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/allocation_planner.cc#L2532).
- [ort_value_pattern_planner.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/ort_value_pattern_planner.cc) traces lifetimes through [TraceAllocation](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/ort_value_pattern_planner.cc#L33) and emits [GeneratePatterns](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/ort_value_pattern_planner.cc#L55).
- [execution_frame.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/execution_frame.cc) materializes buffers per run: [AllocateAsPerAllocationPlan](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/execution_frame.cc#L761) follows the precomputed recipe.
- [bfc_arena.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/bfc_arena.cc) is the best-fit-coalescing allocator — [Alloc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/bfc_arena.cc#L271), [SplitChunk](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/bfc_arena.cc#L436), [Merge](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/bfc_arena.cc#L568), and a stream-aware variant at [line 850](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/bfc_arena.cc#L850).
- [kernel_registry_manager.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/kernel_registry_manager.cc) resolves ops to kernels: [SearchKernelRegistry](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/kernel_registry_manager.cc#L60) and [CreateKernel](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/kernel_registry_manager.cc#L18).
- [memcpy.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/memcpy.cc) is the tiny [Memcpy::Compute](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/memcpy.cc#L13) kernel that bridges devices.
- [threadpool.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/common/threadpool.cc) implements [ParallelForFixedBlockSizeScheduling](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/common/threadpool.cc#L413) over the Eigen-derived work-stealing pool.

## Before anything runs: kernels, plans, and the fallback

Initialization is where the engine earns its steady state. After the graph transforms have fused and rewritten the model — the subject of the first tour — [SessionState::FinalizeSessionState](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/session_state.cc#L1636) locks in three artifacts. First, kernels: [SessionState::CreateKernels](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/session_state.cc#L292) asks the [KernelRegistryManager](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/kernel_registry_manager.cc#L18) to construct a kernel instance per node, and that manager's [SearchKernelRegistry](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/kernel_registry_manager.cc#L60) walks every registered registry comparing op, version, type constraints, and execution-provider capability until one matches. This is why a session cannot gain provider support mid-run: the kernel objects were built for one specific partition, with attributes and constant initializers already attached. Second, plans. [PlannerImpl::CreatePlan](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/allocation_planner.cc#L2393) runs the topological walk twice, essentially — once to assign every node to a device via the [DeviceBasedPartitioner](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/allocation_planner.cc#L2532), deciding where weights and activations will live, and once to build the per-node allocation recipe. Where a provider cannot claim a node, [GetCpuPreferredNodes](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/fallback_cpu_capability.cc#L44) keeps the CPU EP from over-reaching by preferring nodes whose weights are small enough to matter and whose placement would not trigger a cascade of copies.

Third, memory patterns. The [OrtValuePatternPlanner](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/ort_value_pattern_planner.cc#L33) replays the plan in miniature: every [TraceAllocation](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/ort_value_pattern_planner.cc#L33) and [TraceFree](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/ort_value_pattern_planner.cc#L44) records a buffer's lifetime, and [GeneratePatterns](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/ort_value_pattern_planner.cc#L55) folds them into a MemoryPatternGroup — a block layout in which activations that never overlap can share one arena region. The session state caches these groups keyed on the shapes of the input tensors: [UpdateMemoryPatternGroupCache](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/session_state.cc#L1241) stores the first match it computes, and [ResolveMemoryPatternFlag](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/session_state.cc#L1195) decides whether patterns are even legal, which depends on whether the model has run-to-run shape variability. Fixed-batch deployments — the common inference server case — hit the cached pattern on run two and reuse it forever. This is the same weight-reuse philosophy we saw in the TurboMind block manager of [lmdeploy-2](/lmdeploy-2/), just expressed in C++ allocator terms instead of token-block terms.

## One run, many streams

The executor itself is refreshingly small once the precomputation is done. [ExecuteThePlan](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/sequential_executor.cc#L686) builds a fresh ExecutionFrame, feeds the inputs, and drives the node loop; [ExecuteKernel](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/sequential_executor.cc#L527) is the per-node body that resolves OrtValues, wraps them in a kernel context, and calls Compute. What makes this loop modern is that it is stream-first: the engine no longer pretends there is one global execution thread. Instead, [DeviceStreamCollection](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/device_stream_collection.cc#L145) holds one stream per logical execution lane — typically one per device, plus extra ones a model may have declared with a loop or an if — and [SetDeviceStream](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/device_stream_collection.cc#L154) wires concrete handles into those lanes at run start. A run that touches two devices gets two lanes; a node on lane A that consumes a tensor produced on lane B must wait for a notification, and that is exactly what the [StreamExecutionContext](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/stream_execution_context.cc#L12) tracks with its notification table and countdown barriers.

The abstraction that keeps this device-neutral lives in [stream_handles.h](https://github.com/microsoft/onnxruntime/blob/main/include/onnxruntime/core/framework/stream_handles.h): a Stream with CreateNotification and Flush, and a Notification the consumer can wait on. The framework ships a default implementation in [plugin_ep_stream.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/plugin_ep_stream.cc#L37) — its [WaitNotificationOnDevice](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/plugin_ep_stream.cc#L24) is an honest placeholder that busy-waits on host — and providers override it. The CUDA override is the instructive one: [CudaStream](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/providers/cuda/cuda_stream_handle.cc#L64) wraps a cudaStream_t, and its [CreateNotification](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/providers/cuda/cuda_stream_handle.cc#L114) produces a real event-based cross-lane wait. The subtle piece is host-side work: when a kernel needs to write a value that only becomes known mid-run (a shape, a dynamic dimension), the CUDA path cannot block the device, so [EnqueDeferredCPUBuffer](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/providers/cuda/cuda_stream_handle.cc#L125) parks the host buffer in a queue that [CleanUpOnRunEnd](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/providers/cuda/cuda_stream_handle.cc#L163) drains after the stream has actually finished — the DeferredCpuAllocator at [line 11](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/providers/cuda/cuda_stream_handle.cc#L11) exists to make that buffering transparent to the caller. Cross-lane data movement itself is just a node: the [Memcpy](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/memcpy.cc#L13) kernel gets inserted by the planner wherever a consumer's device differs from its producer's, and [GetStreamForDevice](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/device_stream_collection.cc#L178) decides which lane executes it.

## The frame and the arena: where every byte comes from

On the first run with a new input signature, the ExecutionFrame earns its keep. [IExecutionFrame::Init](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/execution_frame.cc#L258) binds feeds to OrtValue slots; [AllocateMLValueTensorSelfOwnBuffer](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/execution_frame.cc#L535) handles the naive case where a tensor owns its own buffer; and [AllocateAsPerAllocationPlan](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/execution_frame.cc#L761) handles the fast case — it consults the precomputed plan, and when a memory pattern exists, every activation in the group is carved out of a single arena reservation at fixed offsets. [CreateNodeOutputMLValueImpl](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/execution_frame.cc#L883) then hands those regions to the kernels as writable tensors, and [ExecutionFrame::GeneratePatterns](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/execution_frame.cc#L982) is the bridge that turns a planner's group into real buffer geometry. Underneath all of it sits the arena. [BFCArena](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/bfc_arena.cc#L271) — best-fit with coalescing, the same design PyTorch's caching allocator made famous — takes big chunks from the device allocator via [Extend](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/bfc_arena.cc#L98), splits them through [SplitChunk](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/bfc_arena.cc#L436) into size-ordered bins, and rejoins freed neighbors through [Merge](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/bfc_arena.cc#L568). The payoff shows up on the second run: [Free](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/bfc_arena.cc#L475) returns blocks to bins instead of the device, so steady-state inference does zero device allocator calls for activations. The stream-aware variant at [AllocOnStream](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/bfc_arena.cc#L850) sharpens this per lane, and when memory pressure bites, [DumpMemoryLog](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/framework/bfc_arena.cc#L721) prints the bin-by-bin accounting that turns "why is my GPU OOM" into an answer.

The last layer is concurrency inside kernels themselves. Most heavy kernels do not monoprocess their input; they chop it into blocks and call [ParallelForFixedBlockSizeScheduling](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/common/threadpool.cc#L413) on the intra-op pool, which schedules fixed-size chunks across worker threads with the deterministic block ordering the profiler-facing [ThreadPoolProfiler](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/common/threadpool.cc#L50) machinery records. The pool is a vendored, heavily modified Eigen work-stealing pool: [ThreadPoolTempl](https://github.com/microsoft/onnxruntime/blob/main/include/onnxruntime/core/platform/EigenNonBlockingThreadPool.h#L795) drives lock-free queues implemented as the spsc RunQueue at [line 495](https://github.com/microsoft/onnxruntime/blob/main/include/onnxruntime/core/platform/EigenNonBlockingThreadPool.h#L495), with the ThreadPoolLoop shim at [line 403](https://github.com/microsoft/onnxruntime/blob/main/include/onnxruntime/core/platform/EigenNonBlockingThreadPool.h#L403) bridging to Eigen's own primitives. So a GEMM on CPU is three systems deep — the MLAS kernel from the first tour, the pool feeding its blocks, and the arena holding its operands — and all three were shaped by the same decision: do the expensive thinking once, at Initialize, so Run() only executes.

## From Install to Your First Model

Everything above is on by default after `pip install onnxruntime` or `onnxruntime-gpu`. The knobs that expose the machinery: session options control intra-op and inter-op thread counts, arena settings like `arena_extend_strategy` choose between growing the arena in kArenaAllocation steps and reusing device allocator memory, and `enable_mem_pattern` toggles the whole pattern system for debugging. When a run behaves oddly, `ORT_DEBUG_NODE_IO` and the memory-pattern dump give the two most direct windows into this layer — the arena's DumpMemoryLog output is genuinely one of the most readable allocator reports in the ecosystem.

Honest limits: this walk focused on the CPU-plus-CUDA path because that is where the code is complete; the WebGPU, NNAPI, and Core ML providers implement the same Stream/Notification contracts with their own quirks that we did not read. We read code, not benchmarks — the "allocation is pre-computed" claim is structural, but real-world wins depend on shape stability, and a model with dynamic batch sizes will spend its runs in the slower self-owned-buffer branch. And the executor is mid-migration: the old class-based executors are gone, the stream-based loop above is the present, and the training stack shares it with extensions we deliberately skipped. For context: [vLLM](/vllm-2/) and [SGLang](/sglang-3/) solve the same memory-recycling problem at the request level with paged KV blocks, [TensorRT-LLM](/tensorrt-llm-2/) precomputes allocation inside an engine build step, and [OpenVINO](/openvino/) answers on CPU with its own plugin allocator scheme. ONNX Runtime's answer — plan once, pattern-cache, arena-recycle, stream-barrier — is the most explicit and most inspectable of the lot, which is exactly why it rewards this second reading.
