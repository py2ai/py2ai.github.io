Most vector-search libraries hand you an index and stop there. txtai, from NeuML, takes the wider view: it is an embeddings database — a Python platform where you index text, documents, audio, images and video, keep the original content in SQL, link records into a graph network, and then query everything semantically, lexically, or through LLM-driven agents. The README's pitch is refreshingly blunt: up and running in minutes with pip, run local so your data never leaves the machine, scale up only when you need to.

I spent an afternoon walking the source tree on the master branch. txtai targets Python 3.11+ and is built on [Hugging Face Transformers](https://github.com/huggingface/transformers), Sentence Transformers and FastAPI, all under an Apache 2.0 license. What struck me most is how small the core object graph is: one `Embeddings` facade owns every subsystem, and each subsystem gets its own package with a tiny factory that reads your YAML config. The two diagrams below were generated directly from the code paths I traced, and every node in them links back to the exact file and line in the repository — so you can treat this post as a map and jump straight into the code whenever something looks interesting.

This is a read-order tour: the engine first, then the storage and scoring plumbing underneath it, then the runtime layer that turns a local index into an API service, a task graph, or an agent's memory.

## Reading the overview from left to right

- **[Embeddings](https://github.com/neuml/txtai/blob/master/src/python/txtai/embeddings/base.py#L21)** is the center of gravity. The class holds every handle the engine needs — `ann`, `database`, `graph`, `scoring`, `model` — and exposes the verbs you actually call: `index()` at [L102](https://github.com/neuml/txtai/blob/master/src/python/txtai/embeddings/base.py#L102), `upsert()` at [L154](https://github.com/neuml/txtai/blob/master/src/python/txtai/embeddings/base.py#L154), `search()` at [L355](https://github.com/neuml/txtai/blob/master/src/python/txtai/embeddings/base.py#L355) and `similarity()` at [L405](https://github.com/neuml/txtai/blob/master/src/python/txtai/embeddings/base.py#L405).
- **[Vectors](https://github.com/neuml/txtai/blob/master/src/python/txtai/vectors/base.py#L20)** is the vectorization base class: `index()` at [L119](https://github.com/neuml/txtai/blob/master/src/python/txtai/vectors/base.py#L119) batches documents, `transform()` at [L205](https://github.com/neuml/txtai/blob/master/src/python/txtai/vectors/base.py#L205) converts one document into a similarity vector. The [VectorsFactory](https://github.com/neuml/txtai/blob/master/src/python/txtai/vectors/dense/factory.py#L19) picks a concrete backend, with [STVectors](https://github.com/neuml/txtai/blob/master/src/python/txtai/vectors/dense/sbert.py#L18) wrapping sentence-transformers models as the everyday choice.
- **[ANN](https://github.com/neuml/txtai/blob/master/src/python/txtai/ann/base.py#L11)** is the vector index wrapper: `append()` at [L51](https://github.com/neuml/txtai/blob/master/src/python/txtai/ann/base.py#L51) ingests vectors, `search()` at [L71](https://github.com/neuml/txtai/blob/master/src/python/txtai/ann/base.py#L71) runs batched nearest-neighbor queries. The [ANNFactory](https://github.com/neuml/txtai/blob/master/src/python/txtai/ann/dense/factory.py#L22) selects the backend — the zero-dependency [NumPy](https://github.com/neuml/txtai/blob/master/src/python/txtai/ann/dense/numpy.py#L17) scan, [Faiss](https://github.com/neuml/txtai/blob/master/src/python/txtai/ann/dense/faiss.py#L34), or [HNSW](https://github.com/neuml/txtai/blob/master/src/python/txtai/ann/dense/hnsw.py#L22) via hnswlib.
- **[Database](https://github.com/neuml/txtai/blob/master/src/python/txtai/database/base.py#L15)** is the content store: `insert()` at [L43](https://github.com/neuml/txtai/blob/master/src/python/txtai/database/base.py#L43) writes rows, `search()` at [L116](https://github.com/neuml/txtai/blob/master/src/python/txtai/database/base.py#L116) executes SQL with similarity ordering. The [SQLite](https://github.com/neuml/txtai/blob/master/src/python/txtai/database/sqlite.py#L11) backend is the default, and [DatabaseFactory](https://github.com/neuml/txtai/blob/master/src/python/txtai/database/factory.py#L15) also supports server RDBMS options.
- **[Scoring](https://github.com/neuml/txtai/blob/master/src/python/txtai/scoring/base.py#L6)** powers lexical and sparse retrieval: [TFIDF](https://github.com/neuml/txtai/blob/master/src/python/txtai/scoring/tfidf.py#L24) at [ScoringFactory](https://github.com/neuml/txtai/blob/master/src/python/txtai/scoring/factory.py#L15), [BM25](https://github.com/neuml/txtai/blob/master/src/python/txtai/scoring/bm25.py#L13) extending TFIDF, and the [Sparse](https://github.com/neuml/txtai/blob/master/src/python/txtai/scoring/sparse.py#L15) backend for learned sparse embeddings.
- **[Graph](https://github.com/neuml/txtai/blob/master/src/python/txtai/graph/base.py#L10)** builds a relationship network over indexed rows via [GraphFactory](https://github.com/neuml/txtai/blob/master/src/python/txtai/graph/factory.py#L12), enabling path queries, topic modeling and graph-enhanced ranking.
- **[Workflow](https://github.com/neuml/txtai/blob/master/src/python/txtai/workflow/base.py#L25)** orchestrates callable tasks as a DAG; `__call__()` at [L51](https://github.com/neuml/txtai/blob/master/src/python/txtai/workflow/base.py#L51) streams elements through it, backed by the [Execute](https://github.com/neuml/txtai/blob/master/src/python/txtai/workflow/execute.py#L13) scheduler.
- **[Agent](https://github.com/neuml/txtai/blob/master/src/python/txtai/agent/base.py#L14)** is the LLM loop: `__call__()` at [L67](https://github.com/neuml/txtai/blob/master/src/python/txtai/agent/base.py#L67) runs tool-augmented sessions whose tools are your own embeddings instances and task graphs, assembled by [ProcessFactory](https://github.com/neuml/txtai/blob/master/src/python/txtai/agent/factory.py#L11).
- **[API](https://github.com/neuml/txtai/blob/master/src/python/txtai/api/base.py#L12)** extends [Application](https://github.com/neuml/txtai/blob/master/src/python/txtai/app/base.py#L21) to serve a configured index over HTTP; `create()` at [L32](https://github.com/neuml/txtai/blob/master/src/python/txtai/api/application.py#L32) assembles the FastAPI app that uvicorn runs. There is also a [Console](https://github.com/neuml/txtai/blob/master/src/python/txtai/console/base.py#L25) REPL for poking at an index interactively.

## The engine's two paths

Almost everything in txtai happens along two paths. The indexing path starts at `Embeddings.index()`: documents stream in through a `Stream` helper, each one goes to the vector model, the resulting vectors are appended to the ANN index, the raw content is inserted into the database, term weights land in the scoring index, and — if you enabled graph support — relationships are linked as it goes. The query path starts at `Embeddings.search()`: the query is vectorized, the ANN returns candidate neighbors, the database applies SQL where-clauses and joins content back, and hybrid mode fuses the dense ranking with the sparse one.

That hybrid search is worth pausing on. The [Hybrid](https://github.com/neuml/txtai/blob/master/src/python/txtai/embeddings/search/hybrid.py#L8) class blends dense vector results with sparse scoring results, which is how txtai gets both "matches the meaning" and "matches the exact keyword" behavior from one call. Dense retrieval alone is famously bad at rare terms — product codes, error strings, names — and a BM25 term index alone misses paraphrases. txtai runs both and merges the rankings, and the whole mechanism lives in one small file you can read in minutes.

The third interesting path is explanation. `Embeddings.explain()` at [L446](https://github.com/neuml/txtai/blob/master/src/python/txtai/embeddings/base.py#L446) annotates results with the terms that drove the match, which sounds cosmetic until you have to debug why a query keeps surfacing the wrong documents — then it is the difference between guessing and knowing.

## Backends everywhere, config decides

The detail diagram makes txtai's design philosophy obvious: every subsystem is an interface plus a factory plus N interchangeable backends. Dense vectors come from sentence-transformers ([STVectors](https://github.com/neuml/txtai/blob/master/src/python/txtai/vectors/dense/sbert.py#L18)) or an [ONNX](https://github.com/neuml/txtai/blob/master/src/python/txtai/vectors/dense/onnx.py#L25) encoder graph for optimized inference — the same model-serialization trick we covered in our [ONNX runtime tour](/onnx/), and a reminder of how far a quantized encoder graph goes. ANN indexes come from NumPy, faiss, or HNSW, and there is even a pgvector option for teams that want Postgres to own the vectors — our [pgvector walkthrough](/pgvector/) covers that side of the world. Content lives in SQLite by default or in an external RDBMS.

Because every backend is chosen by a factory reading your YAML config, swapping faiss for hnswlib or SQLite for Postgres is a configuration edit, not a code change. The factories are all tiny — `ANNFactory` at [L22](https://github.com/neuml/txtai/blob/master/src/python/txtai/ann/dense/factory.py#L22), `ScoringFactory` at [L15](https://github.com/neuml/txtai/blob/master/src/python/txtai/scoring/factory.py#L15), `DatabaseFactory` at [L15](https://github.com/neuml/txtai/blob/master/src/python/txtai/database/factory.py#L15), `GraphFactory` at [L12](https://github.com/neuml/txtai/blob/master/src/python/txtai/graph/factory.py#L12) — and they follow the same registry shape, so once you have read one you have effectively read them all.

## From Install to Your First Model

Everything below is straight from the README, and it genuinely is two lines before you have a working semantic index.

First, install the package:

```bash
pip install txtai
```

Then build and query an index in Python:

```python
# Get started in a couple lines
import txtai

embeddings = txtai.Embeddings()
embeddings.index(["Correct", "Not what we hoped"])
embeddings.search("positive", 1)
# [(0, 0.29862046241760254)]
```

No model name, no vector dimension, no preprocessing script: the defaults pick a sentence-transformers encoder, download it on first use, and vectorize your documents. The returned tuple is the document id and its similarity score — `0` is the id of `"Correct"`, the only positive sentence in the corpus.

The second way to run txtai is as a service. Point a YAML file at the model and start uvicorn:

```yaml
# app.yml
embeddings:
    path: sentence-transformers/all-MiniLM-L6-v2
```

```bash
CONFIG=app.yml uvicorn "txtai.api:app"
curl -X GET "http://localhost:8000/search?query=positive"
```

That is the whole deployment story for a single-node instance: the YAML config instantiates the same `Embeddings` object you built in Python, and the FastAPI application exposes search over HTTP. From there the config can declare workflows, agents and more, all served by the same process — the README's stated model is "simple microservices or multi-model workflows" joined by task graphs.

## Workflows and agents: the engine as a component

The runtime layer is where txtai stops being a library and starts being a platform. A [Workflow](https://github.com/neuml/txtai/blob/master/src/python/txtai/workflow/base.py#L25) is a set of tasks with declared connections; `WorkflowFactory` at [L9](https://github.com/neuml/txtai/blob/master/src/python/txtai/workflow/factory.py#L9) — loaded from config — and the `Execute` engine at [L13](https://github.com/neuml/txtai/blob/master/src/python/txtai/workflow/execute.py#L13) stream elements through the graph, scheduling independent tasks in parallel. The tasks themselves are ordinary callables: a transcription model, a summarizer, an embeddings index — each one consumes the output of the previous stage. In other words, the "workflow tasks" in the YAML are component runners over txtai's own processing tasks, and the API service exposes them as HTTP endpoints.

An [Agent](https://github.com/neuml/txtai/blob/master/src/python/txtai/agent/base.py#L14) then closes the loop: it wraps an LLM, binds tools — your embeddings instances, your workflows, even other agents — and runs the tool-augmented reasoning loop in `__call__()` at [L67](https://github.com/neuml/txtai/blob/master/src/python/txtai/agent/base.py#L67). A retrieval-augmented generation system stops being a script you wrote and becomes a named process with a config entry, which is exactly what you want once a second application needs the same behavior. The README also documents web and MCP APIs, with bindings for JavaScript, Java, Rust and Go, so the same index can back a web app, a chat client and an MCP-connected assistant.

This layered shape — one engine, many task graphs over it, agents on top — is the same trajectory we saw in our [LlamaIndex tour](/llama-index/), but txtai arrives at it from the database direction rather than the framework direction, and the difference shows in how little ceremony surrounds the engine itself. The Transformers substrate underneath is the same one we walked through in [our Transformers architecture post](/transformers/).

## Honest Limits

A few things worth knowing before you build on it, all verifiable in the source or README:

- **Writes need synchronization.** The `Embeddings` docstring at [L31](https://github.com/neuml/txtai/blob/master/src/python/txtai/embeddings/base.py#L31) states it plainly: indexes are thread-safe for read operations, but writes must be synchronized by your application. Reads can scale across threads; a concurrent write strategy is your problem to coordinate.
- **Python 3.11+ only.** The README is explicit about the floor, so older environments need to upgrade first.
- **The batteries-included core pulls real dependencies.** A minimal install gets you far, but the README also advertises a low footprint with optional extras — the trade is that faiss, hnswlib, audio, video and LLM integrations are additional installs you opt into per feature.
- **First use downloads models.** The default path needs a sentence-transformers encoder, so the very first index build involves a model download; offline environments must pre-seed the model cache.
- **Quality is a function of your chosen encoder.** txtai is model-agnostic, which means result quality tracks whatever embedding model you configure — the engine will faithfully organize whatever representations that model produces.
- **No benchmark theater.** The README makes capability claims, not speed claims; for the numbers that matter you will want to run your own queries against your own corpus, which the example notebooks make straightforward.

None of these are disqualifying — they are the honest edges of a design that puts one very solid engine in the middle and lets configuration decide everything else. If your problem is "index my content, query it semantically, serve it over an API, and let an LLM reason over it," the source shows a clean path from two lines of Python to exactly that.
