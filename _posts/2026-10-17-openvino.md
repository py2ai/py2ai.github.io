Our recent tours have lived close to the GPU: [TensorRT-LLM's](/tensorrt-llm-2/) process lattice, [vLLM's](/vllm-2/) core engines, [SGLang's](/sglang-3/) router fan-out. This visit goes somewhere quieter and, arguably, harder — the CPU. OpenVINO has been shipping since before "inference framework" was a job title, and its CPU plugin is one of the most complete hand-optimized graph executors anywhere in open source. The question this tour asks is the user's-eye question: what actually happens between `core.compile_model(model, "CPU")` and `request.infer()`? The answer runs through a facade that hides its own implementation, a plugin registry loaded from an XML file, a content-addressed cache that can skip compilation entirely, a graph engine with a strict ordering of setup passes, a factory of node classes that now includes attention and MLP kernels, and a threading layer that pins stream threads to physical cores. As always, this is an educational walk through the published code of openvinotoolkit/openvino on the master branch, under the Apache-2.0 license.

The headline discovery is how literal the word "compile" is here. `compile_model` is a genuine compiler invocation — clone the graph, run transformation lists, pick primitive descriptors per node, resolve in-place edges — and the result is hashed so a second process can import a serialized blob instead of repeating the work. The second discovery is that one CompiledModel owns not one graph but one per stream, each fully configured and ready to execute, with a guard object handing them out and re-initializing on shape changes.

<p><em>The overview: the ov::Core facade delegates to CoreImpl, which hashes models into the ModelCache and dispatches to the CPU plugin; the plugin builds a CompiledModel that owns one Graph per stream, wraps each SyncInferRequest in an AsyncInferRequest backed by the generic stage machinery, and executes everything on CPUStreamsExecutor threads.</em></p>

Reading the overview from left to right:

- The public facade at [src/inference/src/cpp/core.cpp](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/cpp/core.cpp#L60) — an inner `Impl` class that extends CoreImpl, keeping the header clean while all logic lives in the dev layer.
- [CoreImpl](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/core_impl.cpp#L559) owns the plugin registry, the device dispatch table, and the compile/import entry points.
- [ModelCache](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/compilation_context.cpp#L66) computes a model hash and stores or imports compiled blobs on disk.
- The CPU plugin's [Plugin::compile_model](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/plugin.cpp#L347) clones, transforms, counts streams, and hands a CompiledModel back.
- [CompiledModel](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/compiled_model.cpp#L77) builds one Graph per stream and manufactures requests through [create_infer_request](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/compiled_model.cpp#L239).
- The [Graph](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L413) configures, allocates, and executes a topological node sequence drawn from the [NodesFactory](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/nodes_factory.cpp#L138) registry.

## A facade, a registry, and a content-addressed cache

Start where every user starts. [Core's constructor](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/cpp/core.cpp#L65) allocates an inner `Impl` — and that `Impl` is not a pimple of raw fields but a subclass: `Core::Impl : CoreImpl` at [line 60](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/cpp/core.cpp#L60). Everything the public class appears to do, it actually inherits from the dev-layer implementation in [core_impl.cpp](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/core_impl.cpp#L559). The first thing CoreImpl does is read a plugin XML: [register_plugins_in_registry](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/core_impl.cpp#L746) parses device names, library paths, and device properties into a registry, and [build_dispatch_entries](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/core_impl.cpp#L55) turns the wildcard patterns — `CPU`, `GPU`, `HETERO:GPU,CPU` — into an ordered dispatch table, with [get_internal_plugin_name](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/core_impl.cpp#L143) resolving names like `BATCH` to their real plugin. Asking for a device that maps to another device is resolved here, long before any model is seen.

[read_model](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/cpp/core.cpp#L80) is thin — it routes through the model reader at [src/inference/src/model_reader.cpp](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/model_reader.cpp#L117), which sniffs XML versus ONNX versus a pre-serialized blob and deserializes into an `ov::Model`. The weight is on [compile_model](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/cpp/core.cpp#L108): four overloads taking a model, a device string, and configuration as remote context, path, or plain map, funneled into [one CoreImpl method](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/core_impl.cpp#L1143). Before the plugin is ever called, [apply_auto_batching](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/core_impl.cpp#L1486) rewrites the device — `CPU` with the AUTO_BATCH hint becomes the BATCH plugin wrapping CPU — and the config is normalized. Then [compile_model_and_cache](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/core_impl.cpp#L1901) consults the cache: [get_cache_model_path](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/core_impl.cpp#L368) builds the directory, [get_model_hash_sync_key](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/core_impl.cpp#L389) builds the sync file name, and the actual fingerprint is [ModelCache::compute_hash](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/compilation_context.cpp#L108) — a digest over the model itself plus every relevant compile option. On a miss, the plugin compiles and the result is stored behind a [CompiledBlobHeader](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/compilation_context.cpp#L186) that versions the format; on a hit, [import_model](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/core_impl.cpp#L1292) hands the bytes to the plugin's import path and the entire compilation is skipped. For a large LLM graph this is the difference between minutes and milliseconds on process start.

## compile_model: clone, transform, count your streams

Down in the plugin, [Plugin::compile_model](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/plugin.cpp#L347) opens with something that surprises people: [the model is cloned](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/plugin.cpp#L373) before a single transformation runs. The reason is API honesty — the user's `ov::Model` must remain exactly as they built it, because they may compile it again for another device or read its ops for debugging. The clone then walks a fixed transformation sequence: [UpToLpt](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/plugin.cpp#L385) lifts low-precision conversions upward so quantized data flows as int8 as far as possible, [PostLpt](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/plugin.cpp#L394) cleans up what remains, the stream count is decided by [calculate_streams](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/plugin.cpp#L387) from the performance hint and core topology, [Snippets](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/plugin.cpp#L395) fuses eligible subgraphs into JIT-generated kernels, and [CpuSpecificOpSet](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/plugin.cpp#L397) validates that every operation has a CPU implementation. Only then does [the CompiledModel get constructed](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/plugin.cpp#L431). The plugin also exposes [get_property](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/plugin.cpp#L443) and [query_model](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/plugin.cpp#L721), the latter letting tools ask which nodes would fall back before paying for compilation.

The [CompiledModel constructor](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/compiled_model.cpp#L77) is where the concurrency model appears. It first creates its [task and callback executors](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/compiled_model.cpp#L94) — the task executor is a stream executor sized by the stream count, and every asynchronous request produced by this model shares it. Then comes the most distinctive choice: [one graph per stream](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/compiled_model.cpp#L124), each fully built and configured, so two in-flight requests never fight over mutable primitive state; [sub-stream handling](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/compiled_model.cpp#L152) covers the case where a model is internally split across streams. Access is arbitrated by [get_graph](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/compiled_model.cpp#L180), which returns a `GraphGuard::Lock` — an RAII handle — and picks the graph by [socket affinity](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/compiled_model.cpp#L189) so a request lands on the graph whose memory sits nearest. On a shape change the guard re-runs [Init and Activate](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/compiled_model.cpp#L216) instead of rebuilding the world. Request creation is a pair of factory methods — [create_sync_infer_request](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/compiled_model.cpp#L234) and the async wrapper at [line 239](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/compiled_model.cpp#L239).

## Configure: making nodes executable

The graph's own lifecycle lives in [graph.cpp](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L113), and its heart is [Configure](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L413) — an ordered list of passes where the order is the whole idea. [SortTopologically](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L416) fixes an execution sequence first, because everything downstream assumes it. [InitNodes](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L417) replaces the framework-agnostic ops with plugin node objects, resolved through the registry: [NodesFactory](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/nodes_factory.cpp#L138) maps operation type names to constructors via the [INTEL_CPU_NODE macro](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/nodes_factory.cpp#L136), and the include list at the top of the file is a small museum — alongside Convolution and MatMul sit the LLM-era registrations pulled in at [lines 119 through 127](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/nodes_factory.cpp#L119): RoPE, scaled attention, RMS norm, QKV projection, paged attention, and an MLP node.

Then the memory-planning passes. [ApplyCommonGraphOptimizations](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L419) folds and fuses what it can; [InitDescriptors](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L423) gives each node a chance to declare candidate implementations, from which [InitOptimalPrimitiveDescriptors](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L427) selects — the decision procedure is [selectOptimalPrimitiveDescriptor](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/node.cpp#L260) in the node base class, weighing precision support against conversion costs. [ResolveInplaceDirections](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L425) and the node-side [canBeInPlace](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/node.cpp#L490) decide which outputs can be written over their inputs, saving a copy per eligible edge — a meaningful win when tensors are activations of a transformer layer. [ResolveEdgeConflicts](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L429) inserts copies where an edge serves consumers wanting different memory layouts, [ShareReorders](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L431) deduplicates identical layout conversions, and [ApplyImplSpecificGraphOptimizations](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L438) lets nodes do last-mile surgery. Only after Configure does [Activate](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L395) [allocate](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L400) the actual memory and [create the executable constants](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L402). Nothing moves until every node has a primitive it can run.

<p><em>The detail view: the API tier of facade and model reader; the runtime tier of CoreImpl, ModelCache, the compiled-model and request base interfaces, and the generic async stage machinery; the CPU plugin tier of plugin, CompiledModel, and its sync/async requests; the graph engine of Graph, NodesFactory, and the node base class; and the threading tier of the CPU stream executor.</em></p>

Walking the detail diagram, a request crosses every tier in order. The user's tensors enter through the base interfaces — [ISyncInferRequest](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/isync_infer_request.cpp#L97) handles [port lookup](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/isync_infer_request.cpp#L125) and tensor plumbing, while [ICompiledModel](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/icompiled_model.cpp#L29) holds the executor pairs every request shares and its [create_infer_request](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/icompiled_model.cpp#L138) is the template the plugin overrides. Above the sync request sits the generic async wrapper: its constructor [builds a two-stage list](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/iasync_infer_request.cpp#L43) — run the sync infer on the task executor, then fire the user callback on the callback executor — and [start_async](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/iasync_infer_request.cpp#L194) just runs the first stage; [make_next_stage_task](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/iasync_infer_request.cpp#L135) chains to the next stage, and the [final task](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/iasync_infer_request.cpp#L160) settles the promise and invokes the callback. The CPU plugin subclasses this once in [async_infer_request.cpp](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/async_infer_request.cpp#L15) to add a fast path: when the model runs on a single stream, [infer skips the generic stage list](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/async_infer_request.cpp#L27) and executes directly on the stream executor — one less context hop per call.

## Infer: one thread per stream, pinned to silicon

The synchronous request is where tensors become work. [SyncInferRequest::infer](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/infer_request.cpp#L103) reads like the diagram: push every input into the graph via [PushInputData](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/infer_request.cpp#L135), call [Graph::Infer](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/infer_request.cpp#L137), and pull outputs with [PullOutputData](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/infer_request.cpp#L148). When the model was compiled for multiple streams, the request holds [sub-requests](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/infer_request.cpp#L110) — one per stream — and [sub_streams_infer](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/infer_request.cpp#L633) splits the batch across them, each on its own graph. Inside the graph, [Infer](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L1657) picks static or dynamic: [InferStatic](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L1364) walks the precomputed topological order — a tight loop over the node sequence, [execute](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/node.cpp#L828) per node — while [InferDynamic](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L1633) re-checks shapes and can fall back through [ReadyDynamic](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/graph.cpp#L1664) checks when a node cannot keep up with a new shape.

The threading layer underneath is [CPUStreamsExecutor](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/threading/cpu_streams_executor.cpp#L568). Each stream owns a TBB arena, and the executor's bookkeeping — a stream-id queue handed out and returned by [get_stream_id](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/threading/cpu_streams_executor.cpp#L525) — is what lets [CompiledModel](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/compiled_model.cpp#L124) say "graph number three belongs to stream number three." On scheduler entry, an observer pins the thread to a vacant core chosen with NUMA and socket awareness, so a stream that starts life next to its graph's memory stays there; nodes can even request relocation through [toNumaNode](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/node.cpp#L1195). The [execute and run](https://github.com/openvinotoolkit/openvino/blob/master/src/inference/src/dev/threading/cpu_streams_executor.cpp#L582) methods are deliberately boring — submit a task to the arena, wait — because all the sophistication lives in the pinning and the arena constraints.

## From Install to Your First Model

The usual two lines — `pip install openvino`, then `ov.Core()`, `read_model`, `compile_model`, infer — now read as the whole diagram. The knob this tour makes legible is `INFERENCE_NUM_THREADS` and the performance hint: THROUGHPUT sizes multiple streams, and everything downstream — graph count, request splitting, arena sizing — follows from that one decision during `calculate_streams`. Latency-minded users get one stream, and the async fast path keeps the dispatch overhead near zero.

Honest limits: this walk is code reading, not benchmarking — the performance claims here are structural, not measured. We toured the CPU plugin because it is the most self-contained; the same facade fronts GPU and NPU plugins whose compile paths differ substantially after the cache layer. And while the LLM nodes in the factory show exactly where transformer serving entered this codebase, running LLMs on CPU well is its own discipline of quantization and scheduling that this tour only points at. For the wider ecosystem, [TensorRT-LLM](/tensorrt-llm-2/) is the GPU-counterpart worth reading next — same questions, answered with processes and streams of a very different kind — while [LocalAI](/localai/) and [Xinference](/inference/) show how frameworks like this one get embedded behind serving frontends. OpenVINO's answer — one graph per stream, configured once, executed on pinned threads — is the oldest pattern here, and still one of the cleanest.
