Most serving engines we have toured on this blog are monoliths by conviction: vLLM, SGLang, and TGI all pull the scheduler, the sampler, and the CUDA kernels into one process because batch-level coordination demands it. LocalAI bets the other way. It is a Go control plane that ships one binary, and behind that binary every model runs in its own operating-system process, speaking a single gRPC dialect. llama.cpp gets a process, diffusers gets a process, whisper gets a process, and the Go core just spawns them, health-checks them, evicts them, and routes OpenAI-shaped HTTP requests at them. The design is the interesting part: it is what lets a hobbyist swap a GGUF file for a Stable Diffusion checkpoint and a TTS voice model without the server caring that three totally different runtimes are involved. As always, this is an educational walk through the published source of mudler/LocalAI under the MIT license; for contrast with the monolithic style, our second tours of vLLM at /vllm-2/ and SGLang at /sglang-3/ cover the other philosophy in depth.

The repository layout mirrors the bet. The core directory holds the HTTP layer and request orchestration in Go, the pkg/model directory is the process-supervision heart, pkg/grpc defines the client surface every request funnels through, and the backend directory contains the polyglot engine implementations in C++, Go, Python, and Rust, all generated against one protobuf file. Nothing in the Go core imports a model runtime directly; the entire seam is the message contract. That makes the code unusually navigable once you accept that the "model" the Go side manipulates is really a child process handle plus an address.

Reading the overview from left to right:

- The CLI entrypoint at [cmd/local-ai/main.go](https://github.com/mudler/LocalAI/blob/master/cmd/local-ai/main.go#L18) parses options with kong, loads the .env chain, and hands off to the server command.
- The OpenAI-compatible surface is [ChatEndpoint](https://github.com/mudler/LocalAI/blob/master/core/http/endpoints/openai/chat.go#L221), which normalizes messages, builds grammars, runs the MCP tool loop, and writes SSE chunks.
- Request orchestration lives in [ModelInference](https://github.com/mudler/LocalAI/blob/master/core/backend/llm.go#L106), which probes the backend for thinking tags and media markers, loads the model, and assembles the token stream with UTF-8 boundary care.
- Before any backend work, [AcquireGlobalBackendSlot](https://github.com/mudler/LocalAI/blob/master/core/backend/global_admission.go#L46) admits the request into a process-wide concurrency ceiling, mapping overflow to a typed 429.
- The [ModelLoader](https://github.com/mudler/LocalAI/blob/master/pkg/model/loader.go#L86) keeps the resident-model store, coalesces concurrent loads, applies an exponential failure cooldown, and health-checks cached entries.
- Backend discovery and spawning happen in [grpcModel](https://github.com/mudler/LocalAI/blob/master/pkg/model/initializers.go#L75) and [spawnGRPCModel](https://github.com/mudler/LocalAI/blob/master/pkg/model/initializers.go#L131), which pick a free port, start the engine, and wait for readiness.
- The child processes themselves are managed by [startProcess](https://github.com/mudler/LocalAI/blob/master/pkg/model/process.go#L250), which tails stdio and watches for exits.
- On the wire, [pkg/grpc/backend.go](https://github.com/mudler/LocalAI/blob/master/pkg/grpc/backend.go#L61) splits the client surface into an inference half and a control half, and [Client](https://github.com/mudler/LocalAI/blob/master/pkg/grpc/client.go#L30) implements it with per-call dials and busy counting.

## The contract that ate the zoo

The whole architecture hangs off [backend/backend.proto](https://github.com/mudler/LocalAI/blob/master/backend/backend.proto), and the first thing to notice is how much it carries. Beyond Predict and PredictStream for text, the same service exposes image generation and upscaling, video and 3D generation, TTS with streaming, audio transcription including a live bidirectional variant, voice and face verification, reranking, token classification, sound detection, diarization, a key-value store API for embeddings, fine-tuning, and quantization jobs. One service definition, roughly sixty RPCs, and every engine in the backend directory implements as much or as little of it as makes sense. Engines that cannot answer a method simply return Unimplemented, and the Go core treats that as an expected signal rather than a failure, a policy you can watch in action when the loader asks a backend to Free its GPU memory and quietly accepts the refusal.

The Go client surface in [pkg/grpc/backend.go](https://github.com/mudler/LocalAI/blob/master/pkg/grpc/backend.go#L61) is where this contract gets audited. The Backend interface is deliberately composed of two sub-interfaces: [InferenceBackend](https://github.com/mudler/LocalAI/blob/master/pkg/grpc/backend.go#L70), whose methods each perform one discrete inference call, and [ControlBackend](https://github.com/mudler/LocalAI/blob/master/pkg/grpc/backend.go#L106), which holds lifecycle operations and the streaming constructors whose work spans the returned stream. The comment block explains why the split exists: wrappers that track in-flight work, like the distributed router's accounting client, embed only ControlBackend and implement every InferenceBackend method explicitly. Add a method to InferenceBackend and those wrappers stop compiling until someone decides whether the new call should be counted. It is a compile-time forcing function for a bookkeeping question that would otherwise be answered by silence, and it is the kind of detail that separates a multiplexer that scales from one that quietly leaks concurrency.

The client half in [pkg/grpc/client.go](https://github.com/mudler/LocalAI/blob/master/pkg/grpc/client.go#L30) is refreshingly unfancy. Every call dials a fresh connection with a 50 MB message cap at [dial](https://github.com/mudler/LocalAI/blob/master/pkg/grpc/client.go#L72), defers the close, and bumps an inFlight counter through [setBusy](https://github.com/mudler/LocalAI/blob/master/pkg/grpc/client.go#L53). A comment there records a real bug fixed: a boolean busy flag let the first completion of a parallel batch report the engine idle while siblings still ran, so it became a count. Backends that cannot handle parallel requests hold an operation mutex for the duration, and every call fires the watchdog mark through [wdMark](https://github.com/mudler/LocalAI/blob/master/pkg/grpc/client.go#L63) so a stuck engine is attributable. Distributed mode adds bearer-token credentials via the [NewClientWithToken](https://github.com/mudler/LocalAI/blob/master/pkg/grpc/backend.go#L25) constructor, implemented as per-RPC metadata rather than TLS.

## Spawning an engine

When a request names a model that is not resident, the loader's discovery path in [initializers.go](https://github.com/mudler/LocalAI/blob/master/pkg/model/initializers.go#L75) takes over. Backend names pass through [CanonicalBackend](https://github.com/mudler/LocalAI/blob/master/pkg/model/initializers.go#L41), which folds aliases like "llama" and "go-llama" onto the canonical llama-cpp engine. If the model config names a backend explicitly, that engine is used directly; otherwise the loader asks [SelectAutoLoadBackends](https://github.com/mudler/LocalAI/blob/master/pkg/model/initializers.go#L549) for a deterministic, file-type-filtered candidate list, so an audio codec can never win the trial loop for a GGUF model, and then tries each in order until one loads.

Spawning itself is [spawnGRPCModel](https://github.com/mudler/LocalAI/blob/master/pkg/model/initializers.go#L131). External backends can be registered either as a file path or a remote URI; the file path gets a free localhost port and a fresh child process, the URI becomes a plain network client. Then comes the readiness wait at [lines 186 through 198](https://github.com/mudler/LocalAI/blob/master/pkg/model/initializers.go#L186-L198): poll HealthCheck with a bounded attempt count and delay, and if the engine never comes up, [grpcStartupError](https://github.com/mudler/LocalAI/blob/master/pkg/model/initializers.go#L238) digs the last non-empty stderr line out of the child's log so the operator sees "ImportError: no module named diffusers" instead of a bare connection refused. Only after readiness does the loader issue the [LoadModel RPC](https://github.com/mudler/LocalAI/blob/master/pkg/model/initializers.go#L217), passing the model file and options cloned from the shared template, and register the model's estimated byte size with the watchdog for size-aware eviction.

The child's runtime environment gets real attention in [startProcess](https://github.com/mudler/LocalAI/blob/master/pkg/model/process.go#L250). The binary is chmodded executable if needed, each engine gets an owned scratch and state directory so a crashed child cannot strand request files in the shared temp, and the [vulkanICDEnv](https://github.com/mudler/LocalAI/blob/master/pkg/model/process.go#L479) helper appends the backend's bundled Vulkan ICD manifests to the loader search path so GPU backends do not silently fall back to CPU inside minimal containers. Two goroutines tail the child's stdout and stderr into the structured log and an optional ring buffer, and a third watches the [Done channel](https://github.com/mudler/LocalAI/blob/master/pkg/model/process.go#L371) so an exit is reported with its code plus the intentional-stop marker that distinguishes our shutdown from a segfault. That marker exists because a child killed by our own SIGTERM reports exit code negative one, indistinguishable from a signal-induced crash; the loader keeps a stoppingProcs map purely so the log can say "stopped" versus "exited unexpectedly".

## Keeping the fleet honest

Supervision is where the design earns its keep. The cached entry check at [checkIsLoaded](https://github.com/mudler/LocalAI/blob/master/pkg/model/loader.go#L704) is not a map lookup; it probes the engine's health RPC, with a freshness cache to avoid serializing every request behind a network round-trip, and if the child is dead it tears the entry down so the next request gets a fresh spawn. Loading is singleflight by way of a per-model channel map in [loadModel](https://github.com/mudler/LocalAI/blob/master/pkg/model/loader.go#L494): the first requester creates the engine, followers wait on the channel and inherit the result, and a follower whose leader failed gets exactly one retry that bypasses the cooldown.

The cooldown is the nicest bit of defensive engineering here. Every failed load arms an exponential backoff window per model in [recordLoadFailure](https://github.com/mudler/LocalAI/blob/master/pkg/model/loader.go#L197), starting at ten seconds and capped at five minutes, and fresh triggers during the window get a typed [ModelLoadCooldownError](https://github.com/mudler/LocalAI/blob/master/pkg/model/loader.go#L133) that the HTTP layer maps to 503 with Retry-After. Without it, a client polling a broken model spawns and leaks a new engine process on every poll. Shutdown mirrors this care: the graceful [ShutdownModel](https://github.com/mudler/LocalAI/blob/master/pkg/model/loader.go#L621) waits for in-flight calls within a deadline, asks the engine to Free its VRAM first, and escalates to a forced variant used by the watchdog's busy-killer, which fires when an engine has been stuck on one call far past the timeout and will never answer a Free RPC again.

Capacity policy lives in two enforcers called before any load: [enforceGroupExclusivity](https://github.com/mudler/LocalAI/blob/master/pkg/model/initializers.go#L435) evicts every loaded model sharing a concurrency group with the incoming one, then [enforceLRULimit](https://github.com/mudler/LocalAI/blob/master/pkg/model/initializers.go#L415) applies the global cap, both retrying while victims are still busy. The watchdog itself, in [pkg/model/watchdog.go](https://github.com/mudler/LocalAI/blob/master/pkg/model/watchdog.go), ties the per-request marks from the gRPC client to these eviction decisions, so "which models are old" and "which engines are wedged" are answered from the same ledger.

## One request, end to end

Put the pieces together with a streaming chat call. [ChatEndpoint](https://github.com/mudler/LocalAI/blob/master/core/http/endpoints/openai/chat.go#L221) first cleans the message list: blank system turns are stripped so they cannot suppress the model YAML's system prompt, and late system messages are merged or re-rolled per template policy. Functions and response formats compile into a grammar, MCP tool definitions are discovered and injected, and the streaming branch spawns a worker goroutine whose responses arrive on a channel that the request loop forwards as SSE data frames at [line 599](https://github.com/mudler/LocalAI/blob/master/core/http/endpoints/openai/chat.go#L599), closing with a [usage trailer](https://github.com/mudler/LocalAI/blob/master/core/http/endpoints/openai/chat.go#L793) when the client asked for stream_options.include_usage. If the model calls an MCP tool mid-stream, the loop executes it, appends the result as a tool message, re-templates, and runs another inference iteration, up to a configurable cap.

Down in [ModelInference](https://github.com/mudler/LocalAI/blob/master/core/backend/llm.go#L106), the closure that actually talks to the engine is built with visible care. Reasoning-style thinking tags and the multimodal media marker are probed from the backend once per load and persisted only when the probe was allowed to fill them, because persisting a request-scoped value would masquerade as an operator's explicit config. The streaming path accumulates raw bytes and flushes only complete UTF-8 runes at [lines 290 through 306](https://github.com/mudler/LocalAI/blob/master/core/backend/llm.go#L290-L306), so multi-byte characters never split across callback invocations. C++ autoparser chat deltas, when the engine provides them, ride alongside so tool calls and reasoning splits survive the trip. And wrapping the whole closure, the global admission slot is acquired last at [lines 473 through 481](https://github.com/mudler/LocalAI/blob/master/core/backend/llm.go#L473-L481), so queue pressure is measured at the moment of engine contact, not at HTTP receipt.

What deserves stealing from this codebase is the discipline of the seam. Every engine, whatever language it is written in, answers the same sixty-method contract or says Unimplemented; the supervisor knows processes, not models; and the one place where inference and control were at risk of mixing, the client interface, was split until the compiler could enforce the difference. Compare this with the router we toured in /text-generation-inference/, which solved the opposite problem by pulling everything into one Rust process, or the admission and scheduling layers in /litellm-2/, and a pattern emerges: the systems that survive new model architectures are the ones that make their binding decisions at exactly one seam. LocalAI's seam is a child process and a proto file, and after reading the source, it is hard to argue with the choice.
