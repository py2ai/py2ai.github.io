Serving a large model on a GPU is a different sport from running one on a laptop: the difference between a demo and a production endpoint is measured in tokens per second per dollar, and every millisecond of kernel launch overhead and every wasted byte of KV cache shows up on the invoice. TensorRT-LLM is NVIDIA's answer to that invoice. The repository — Apache-2.0-licensed, targeting Python 3.10 and 3.12 on CUDA 13.4 — bundles specialized kernels for the operations that dominate transformer math, a compiled C++ runtime for scheduling and cache management, and a pythonic framework on top so you never have to write CUDA to benefit from it. A 1.4 release candidate, the project sits underneath a large slice of production deployments — it is the engine behind several hosted-model vendors and NVIDIA's reference implementation for each new GPU generation, from Hopper tensor cores to Blackwell attention paths.

The architecture is best understood as one API bolted onto two engines. The front door is the `LLM` class in `tensorrt_llm/llmapi/llm.py` — under two thousand lines that hide process spawning, multi-GPU coordination, and engine selection behind a constructor and a `generate()` call. Its arguments funnel into `llm_args.py`, a six-thousand-line configuration module that normalizes every knob from quantization to parallelism strategy. Requests then flow into one of two execution paths: a compiled C++ engine reached through the Python bindings in `executor/executor.py`, or a pure-PyTorch path in `tensorrt_llm/_torch/` where the model, the scheduler, and the KV cache are ordinary Python objects you can read and subclass. Around both, a serving ring offers an OpenAI-compatible HTTP server, a gRPC surface, a CLI, and disaggregation coordinators that split prefill and decode across machines. As always in this series, what follows is an educational tour of published source code.

Reading the overview from left to right:

- [The LLM class](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/llmapi/llm.py) is the facade that turns a model name and a few options into a running engine.
- [LlmArgs](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/llmapi/llm_args.py) validates and normalizes every engine, cache, and parallelism setting.
- [The Python Executor](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/executor/executor.py) submits requests and streams responses over the C++ bindings.
- [The Torch model engine](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/pyexecutor/model_engine.py) runs the schedule-forward-sample loop in pure PyTorch.
- [The model loader](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/pyexecutor/model_loader.py) maps checkpoints onto live modules with quantization applied.
- [The OpenAI server](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/serve/openai_server.py) exposes chat and completions routes over HTTP.
- [The C++ executor](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/executor) owns request lifecycle, configs, and cache transmission natively.
- [The KV cache manager](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/batch_manager/kvCacheManager.cpp) allocates, evicts, and recycles paged cache blocks.

## Why You Need This

The first reason is the configuration discipline, which is the part most projects get wrong. Every option a user can set — tensor parallelism, expert parallelism, cache size, quantization recipe, speculative decoding strategy, CUDA graph batch sizes — enters through one choke point: [the LLM class](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/llmapi/llm.py) collects them, and [LlmArgs](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/llmapi/llm_args.py) reconciles them into a consistent world state. That file is enormous for a reason: it encodes the compatibility matrix of the entire system, which backends require which cache layouts, which parallelism combinations are legal on which GPU counts, and which defaults change when a model is multimodal. Because the validation lives in one place, the engines below can trust what they receive, and the same file computes derived quantities — cache sizes from GPU memory, worker counts from parallelism settings — so operators describe intent while the system derives the physics. Config as a validated, centralized contract rather than kwargs scattered across twelve constructors: that alone is worth the visit.

The second reason is the Torch-native path, which is where the project became genuinely readable. In `tensorrt_llm/_torch/`, [the model engine](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/pyexecutor/model_engine.py) implements the canonical inference loop — schedule requests, run a forward pass, sample tokens, append to cache, repeat — in ordinary Python you can step through with a debugger. [The model loader](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/pyexecutor/model_loader.py) resolves checkpoints, applies sharding for multi-GPU layouts, and fuses quantization during load; [the model zoo](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/models) holds hand-optimized implementations of Llama, DeepSeek, Qwen and peers. Performance comes from pluggable parts rather than monoliths: [the attention backends](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/attention_backend) let a model run on FlashInfer, TensorRT-LLM's own kernels, or FlashMLA depending on hardware; [CUDA graph capture](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/pyexecutor/cuda_graph_runner.py) eliminates launch overhead on the hot decode path; [speculative decoding](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/speculative) contributes draft-and-verify strategies such as EAGLE, Medusa, and lookahead; and [the MoE directory](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/moe) handles expert routing with fused communication. Reading this half teaches how the tricks you see in papers translate into a production loop.

The third reason is the compiled engine underneath, which shows what the same problem looks like when interpreted Python is no longer fast enough. Below the bindings of [the Python Executor](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/executor/executor.py), the C++ side models the world explicitly: [the request class](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/executor/request.cpp) carries tokens, sampling parameters, and stopping criteria; [the micro-batch scheduler](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/batch_manager/microBatchScheduler.cpp) forms batches each iteration while [the capacity scheduler](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/batch_manager/capacityScheduler.cpp) decides what fits given live KV pressure. [The KV cache manager](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/batch_manager/kvCacheManager.cpp) runs paged allocation with eviction and reuse, and [the data transceiver](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/batch_manager/dataTransceiver.cpp) ships cache blocks between processes — the substrate for disaggregated serving, where prefill runs on one machine and decode on another. The memory layer in [the C++ runtime](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/runtime) supplies tensor buffers, IPC, multicast groups, and NCCL communicators, and the kernel directories — `kernels/`, `flash_mla/`, `deep_gemm/`, `deep_ep/`, CUTLASS extensions — hold the device code behind each attention and MoE call. Around everything sits the serving tier: [the OpenAI server](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/serve/openai_server.py) — thirty-five hundred lines of routes, tool handling, and streaming — with [protocol schemas](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/serve/openai_protocol.py), a gRPC alternative under `grpc/`, [the serve CLI](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/commands/serve.py), and [the disaggregation coordinator](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/serve/disagg_coordinator.py) that matches prefill and decode workers into pairs.

<p><em>The detail view: the Python API layer with facade, config, tokenizer, reasoning parser and MPI sessions; the Torch-native engine from scheduler and CUDA graphs through attention backends, speculative decoding, MoE and disaggregation; the C++ core from request lifecycle through micro-batch scheduling, paged cache and KV transport; and the serving tier of OpenAI routes, coordinators, CLI and gRPC.</em></p>

Walking the detail diagram, one request is traceable end to end. A client posts chat messages to [the OpenAI server](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/serve/openai_server.py), which validates them against [the protocol schemas](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/serve/openai_protocol.py) and hands a prompt to [the LLM facade](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/llmapi/llm.py); [the reasoning parser](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/llmapi/reasoning_parser.py) can split chain-of-thought channels from final answers mid-stream, and [the MPI session](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/llmapi/mpi_session.py) has already arranged the worker processes for a multi-GPU layout. The facade submits through [the Executor bindings](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/executor/executor.py), and the two engines tell one story twice. On the Torch path, [the model engine](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/pyexecutor/model_engine.py) asks [the scheduler](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/pyexecutor/scheduler) which requests run, replays [a captured CUDA graph](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/pyexecutor/cuda_graph_runner.py) for the decode step, and manages pages in [the Torch KV cache](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/pyexecutor/kv_cache). On the C++ path, the same semantics live in compiled classes with the same names and sharper edges, connected by explicit C++ types instead of Python objects.

The second walkthrough worth taking is disaggregation, because it shows a systems design turned into working code. [The coordinator server](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/serve/coordinator_server.py) registers prefill and decode instances and matches them into pairs; [the disaggregation coordinator](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/serve/disagg_coordinator.py) tracks load and routes accordingly; and the transport — [the C++ data transceiver](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/batch_manager/dataTransceiver.cpp) on the compiled path, [the Torch disaggregation module](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/disaggregation) on the other — moves KV blocks so a prompt processed on machine A continues generation on machine B without recomputation. The insight repeats everywhere: the fast path is compiled, the control path is Python, and the boundary between them is a thin, named interface — a pattern even the agent-flavored [scaffolding controller](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/scaffolding/controller.py) follows for multi-step workloads.

## From Install to Your First Model

The supported route is NVIDIA hardware and either a container or pip. The pip route is `pip install tensorrt-llm --extra-index-url https://pypi.nvidia.com`, with CUDA 13 runtime and a compatible driver on the box; the container route pulls a prebuilt image with every CUDA dependency pinned. Your first lines are the whole point of the facade: `from tensorrt_llm import LLM`, then `llm = LLM(model="meta-llama/Llama-3.2-1B-Instruct")`, then `out = llm.generate(["Explain quantum tunneling in one sentence."])` — the constructor builds the engine, spawns workers if parallelism demands it, and loads weights. For chat, `llm.chat([...])` applies a model's chat template, and the streamed variant returns tokens as they arrive. To serve instead of script, `trtllm-serve serve` starts the OpenAI-compatible endpoint assembled by [the serve CLI](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/commands/serve.py) from a YAML config, and any OpenAI client can point at it unchanged. Quantized checkpoints, speculative decoding, and expert parallelism are constructor arguments, not code changes — flip the option, restart, measure.

Honest limits: this is NVIDIA-only in practice — the kernels target CUDA, and the meaningful performance story requires recent datacenter GPUs, so nothing here runs on Apple silicon or consumer AMD cards. The configuration surface is deep enough that wrong combinations surface as exotic failures rather than clean errors, and the project moves quickly enough that API details shift between minor versions — the 1.4 line was still a release candidate while writing. The compiled path builds slowly and debugging it requires C++ and CUDA tooling, and the dual-engine design means some features are ahead on one path than the other. None of that changes the verdict: for anyone serving models on NVIDIA GPUs, TensorRT-LLM's source is the most complete public map of what production inference actually spends its time on.
