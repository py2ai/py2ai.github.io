Most fine-tuning libraries you meet are wrappers: they take Hugging Face Trainer, add a config file, and hope the stock kernels are fast enough. Unsloth is the opposite bet. Instead of orchestrating around transformers, it reaches inside them, replacing attention, MLP, loss, and optimizer internals with hand-tuned Triton kernels and rewritten forward passes, then exposes the result through the same `FastLanguageModel.from_pretrained` API you already know. The payoff is the claim on the README - roughly 2x faster training with far less VRAM and no accuracy loss - and the mechanism is entirely visible in the source: a loader that dispatches by architecture, a family of per-model fast paths descended from one Llama implementation, and a kernel directory that does the arithmetic nobody else wants to write. The release tagged 2026.10.6 under an Apache-2.0 license now also ships a desktop app and CLI, but the training engine remains the heart of the roughly 60,000 lines of Python in the core package.

What makes the codebase worth reading is that it documents its own intrusiveness. Every file is a list of patches with names like `patch_saving_functions` or `patch_trl_async_grpo`, so you can see exactly which upstream behavior is being replaced and why. If you have ever wondered where the memory savings of 4-bit dynamic quantization actually come from, or how a LoRA layer avoids two matmuls per step, the answers are individual functions you can read in an afternoon. As always in this series, what follows is an educational tour of published source code.

Reading the overview from left to right:

- [unsloth/__init__.py](https://github.com/unslothai/unsloth/blob/main/unsloth/__init__.py) is a 1714-line bootstrap that initializes GPU state before anything else imports torch, then re-exports the public API.
- [unsloth/models/loader.py](https://github.com/unslothai/unsloth/blob/main/unsloth/models/loader.py) defines FastLanguageModel at line 1085 and FastModel at line 1992, the 3328-line dispatch table every user entry point flows through.
- [unsloth/models/mapper.py](https://github.com/unslothai/unsloth/blob/main/unsloth/models/mapper.py) is a 1488-line registry whose build_mappers at line 1400 turns model names into architecture identifiers.
- [unsloth/models/llama.py](https://github.com/unslothai/unsloth/blob/main/unsloth/models/llama.py) is the 5097-line parent fast path - FastLlamaModel at line 2987 with rewritten decoder forwards that other architectures inherit.
- [unsloth/models/rl.py](https://github.com/unslothai/unsloth/blob/main/unsloth/models/rl.py) monkey-patches TRL for GRPO, DPO, and friends; PatchFastRL lives at line 5088 of its 5114 lines.
- [unsloth/kernels/rms_layernorm.py](https://github.com/unslothai/unsloth/blob/main/unsloth/kernels/rms_layernorm.py) opens the Triton kernel set: _rms_layernorm_forward at line 26 with a Gemma variant and a full backward pass behind it.
- [unsloth/utils/packing.py](https://github.com/unslothai/unsloth/blob/main/unsloth/utils/packing.py) implements sequence packing at enable_sample_packing line 227, with [utils/attention_dispatch.py](https://github.com/unslothai/unsloth/blob/main/unsloth/utils/attention_dispatch.py) choosing the attention backend per device at scaled_dot_product_attention line 96.
- [unsloth/save.py](https://github.com/unslothai/unsloth/blob/main/unsloth/save.py) closes the loop with unsloth_save_model at line 1118 and GGUF export through save_to_gguf at line 2133.

## Why You Need This

If you have read the tours of [LLaMA-Factory](/llama-factory/) or [axolotl](/axolotl/), you saw the configuration-driven school of fine-tuning: describe the job in YAML, and a dispatcher wires up datasets, trainers, and adapters. Unsloth solves a different problem. It asks what the stock PyTorch modules actually spend time on, then rewrites those specific modules. The result is a library you can drop into an existing training script without changing the script - the loader returns a model that simply has faster insides. That composability is why it shows up as an integration in so many of the other tools in this series rather than competing with them head-on.

The kernel work is the part worth studying on its own. Where [Triton](/triton/) shows you the language and [flash-attention](/flash-attention/) shows you one algorithm, unsloth shows you a whole kernel suite aimed at training: fused RMSNorm with its backward pass, rotary embeddings that write Q and K in place, a LoRA matmul that fuses the base quantized weight and the adapter delta into one call, cross-entropy computed without materializing the full logit matrix, and dequantize-on-the-fly GEMV for NF4 weights. Alongside them sit FP8 and NVFP4 paths that pair naturally with the quantization tour of [llm-compressor](/llm-compressor/) and the FP8 work in [transformer-engine](/transformer-engine/), plus a grouped-GEMM implementation for MoE routing.

The RL story is the other headline. Rather than reimplementing PPO or GRPO, unsloth patches [TRL](/trl/) in place: trainers are wrapped at import time, generation is rerouted through vLLM when available, and asynchronous rollout support is injected - which turns the same GRPO math into something that runs on a single GPU. Combined with [PEFT](/peft/) adapters, [accelerate](/accelerate/) sharding, FSDP2 patches inspired by the same ideas as [torchtitan](/torchtitan/), and optional [DeepSpeed](/deepspeed/) integration, it is a case study in getting performance by repairing upstream code instead of forking it. Even the embedding-model world is covered, since the package ships its own take on [sentence-transformers](/sentence-transformers/) training.

The loading story starts in the loader. FastLanguageModel.from_pretrained at line 1122 of [models/loader.py](https://github.com/unslothai/unsloth/blob/main/unsloth/models/loader.py) normalizes the model name - _strip_unsloth_bnb_4bit_suffix at line 203 removes quantization tags before resolving the base repo - checks that precision flags do not contradict each other at _precision_flags_conflict line 212, and repairs rope inv_freq buffers saved by older transformers through _fix_rope_inv_freq at line 881 with the monkey-patch installed at line 966. The modern FastModel at line 1992 with its own from_pretrained at line 2033 handles the general case including vision and multimodal checkpoints, while FastVisionModel at line 3323 and FastTextModel at line 3327 pin the task type. Names to architectures are resolved by mapper.py, and the catalog side lives in [registry/registry.py](https://github.com/unslothai/unsloth/blob/main/unsloth/registry/registry.py): a QuantType enum at line 11 (bitsandbytes, unsloth dynamic 4-bit, GGUF, bf16), a ModelInfo dataclass at line 35, and register_model at line 104 filling MODEL_REGISTRY from line 101 - _register_models at line 157 is what generates the grid of `unsloth/...` quantized mirror names you download every day.

Once the config is resolved, dispatch lands on the fast path in [models/llama.py](https://github.com/unslothai/unsloth/blob/main/unsloth/models/llama.py). LlamaModel_fast_forward at line 1150 replaces the whole decoder stack, CausalLM_fast_forward at line 1769 wraps it with a fused final projection and loss, PeftModel_fast_forward at line 1986 injects LoRA-aware routing into the peft wrapper, and unsloth_fast_generate at line 2640 gives inference a cache-managed decode loop. The rotary machinery is custom too - LlamaRotaryEmbedding at line 2301 with a LongRopeRotaryEmbedding variant at line 2485 for stretched contexts - and _fused_lora_modules at line 2931 decides which linear layers qualify for the fused kernel. The class that ties it together, FastLlamaModel at line 2987, is what the per-family modules extend: FastQwen3Model at line 365 of [models/qwen3.py](https://github.com/unslothai/unsloth/blob/main/unsloth/models/qwen3.py) and FastGemma2Model at line 639 of [models/gemma2.py](https://github.com/unslothai/unsloth/blob/main/unsloth/models/gemma2.py) each override only what differs, which is why one architecture file can carry the whole family.

The kernels directory is where the speed lives. [kernels/rms_layernorm.py](https://github.com/unslothai/unsloth/blob/main/unsloth/kernels/rms_layernorm.py) spends its 1139 lines on one operation done thoroughly: _rms_layernorm_forward at line 26, a dedicated backward at line 70, and a Gemma-specific variant at line 216 for its different reduction order. [kernels/rope_embedding.py](https://github.com/unslothai/unsloth/blob/main/unsloth/kernels/rope_embedding.py) exposes Fast_RoPE_Embedding at line 222 as a torch.autograd.Function with a QK-split variant at line 305, so rotations are applied in place during both passes. [kernels/fast_lora.py](https://github.com/unslothai/unsloth/blob/main/unsloth/kernels/fast_lora.py) computes the LoRA delta inside _matmul_lora_ext at line 210 instead of adding two separate matmuls; swiglu.py fuses the gated MLP activation in 135 lines; [kernels/cross_entropy_loss.py](https://github.com/unslothai/unsloth/blob/main/unsloth/kernels/cross_entropy_loss.py) avoids the full-vocab logit blowup; and the quantization pair of nf4.py and fp8.py, plus large_head_attention.py for unusual head dimensions and the grouped-GEMM interface at [kernels/moe/grouped_gemm/interface.py](https://github.com/unslothai/unsloth/blob/main/unsloth/kernels/moe/grouped_gemm/interface.py) for MoE experts, round out a suite that spans 977 lines for MoE alone.

Training and RL ride on top. [trainer.py](https://github.com/unslothai/unsloth/blob/main/unsloth/trainer.py) wraps the HF Trainer with a UnslothVisionDataCollator at line 69, wires the fused optimizer from [optimizers/flash_adamw.py](https://github.com/unslothai/unsloth/blob/main/unsloth/optimizers/flash_adamw.py) via imports at line 30, and accepts a q_galore_config parameter at line 940 that activates the Q-GaLore optimizer of [optimizers/q_galore_adamw.py](https://github.com/unslothai/unsloth/blob/main/unsloth/optimizers/q_galore_adamw.py). The RL side is the boldest patching in the repo: [models/rl.py](https://github.com/unslothai/unsloth/blob/main/unsloth/models/rl.py) installs trainer-wide hooks through patch_trl_rl_trainers at line 4380, reroutes generation with patch_trl_vllm_generation at line 4537, and adds async rollouts with patch_trl_async_grpo at line 4925, all surfaced through one PatchFastRL call at line 5088 backed by the 5032 lines of concrete replacements in rl_replacements.py. Preference training gets its own PatchDPOTrainer in [models/dpo.py](https://github.com/unslothai/unsloth/blob/main/unsloth/models/dpo.py), FSDP2 runs through [models/fsdp2.py](https://github.com/unslothai/unsloth/blob/main/unsloth/models/fsdp2.py) and its QLoRA companion, and the memory tricks extend to the model itself - vision.py moves frozen embedding tables to host RAM with offload_input_embedding at line 1051 and restores them at line 1119 when needed.

Saving is where the tour ends, and it is more engineering than it sounds. unsloth_save_model at line 1118 of [save.py](https://github.com/unslothai/unsloth/blob/main/unsloth/save.py) handles adapter versus merged saves, preserves tokenizer quirks through check_if_sentencepiece_model at line 502, and merges LoRA weights layer by layer with _merge_lora at line 677. GGUF is a first-class target: save_to_gguf at line 2133 drives the conversion, unsloth_save_pretrained_gguf at line 4163 is the API entry, a generic fallback at line 5625 covers models without a hand-written conversion recipe, and the llama.cpp toolchain is fetched on demand by install_llama_cpp_clone_non_blocking at line 1727. Around the core, a 485-line raw_text module and a 608-line synthetic-data module under dataprep help you build datasets, and the CLI - whose start command alone is 7697 lines - wraps the desktop experience around the same engine.

## From Install to a Fine-Tuned Model

The README's two-minute path:

```sh
pip install unsloth
```

Then a standard QLoRA session:

```python
from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name = "unsloth/Qwen3-8B",
    max_seq_length = 2048,
    load_in_4bit = True,
)
model = FastLanguageModel.get_peft_model(
    model,
    r = 16,
    target_modules = ["q_proj", "k_proj", "v_proj", "o_proj"],
    lora_alpha = 16,
)
```

The same object trains with any HF Trainer or with TRL after a single `PatchFastRL` call, and saves back to LoRA adapters or a merged GGUF with one line.

Honest limits: the fastest paths assume NVIDIA GPUs and the Triton toolchain, so AMD, Intel, and CPU backends take a compatibility layer rather than the fused code; deep monkey-patching means the library tracks specific transformers and TRL versions and can lag a fresh release by days; and the patch-first design means a debugging session may read three libraries at once. None of that changes the educational value - this is the most complete public map of where LLM training time actually goes.
